# Decisions

Each entry gives the decision, the reason, and the alternatives that we did not keep. Add an entry when a change makes a new decision. Change an entry when a decision changes.

## 1. Two repositories, one direction

- **Decision:** the public repository (core and Community edition) never refers to the private repository (Enterprise edition). The private repository uses the public crates from one Git tag.
- **Why:** the public repository builds and runs alone, and the Enterprise features need no change in the core.
- **Not kept:** cargo feature flags in one repository. They put Enterprise code in the public code.

## 2. Plugins and an edition builder

- **Decision:** a feature, core or Enterprise, is one `Plugin`. It registers its capability, migrations, authenticators, hooks and gRPC services on an `EditionBuilder`. `Edition` has private fields.
- **Why:** one place for each feature, and one recipe for core and Enterprise. A new extension point is a new builder method, so no edition breaks.
- **Not kept:** a struct with one public field for each trait (it broke each edition at each new field, and allowed one guard only); a generic event bus with a type map (harder to read).

## 3. Hooks by event and by resource kind

- **Decision:** one small trait for each event (`BeforeCreate`, `AfterDelete`). A hook is registered for one resource kind. The hooks run in registration order, in the transaction of the core write. The first error stops the run.
- **Why:** a hook implements only what it needs, never filters the kind, and a refusal rolls back the core write and all hook writes together.
- **Not kept:** one trait with all events; hooks after the commit (no rollback).

## 4. Actors

- **Decision:** one table `actors (id, kind, created_at)`. `ActorKind` is open. The core defines the kinds of its features (`user`, `app`), and an edition adds its own. A feature that needs details for a kind adds its own table with `id REFERENCES actors (id)`: `users`, `apps`. An actor has no owner and no role on another actor: it acts only for itself.
- **Why:** a person, a bot or a later kind can act, and each reference keeps a real foreign key. The rights come from the workspaces (see 32), not from a tree of actors.
- **Not kept:** one table for each kind with no common identity (no common foreign key); a pair `(kind, id)` with no foreign key (no integrity); an owner of an actor and the role `delegate` (a second way to give rights, next to the roles in a workspace).

## 5. Workspace and author

- **Decision:** a resource has one container, its workspace (`workspace_id`), and an author (`created_by`). A creation names its workspace. Only a workspace has owners: the rows of `workspace_owners`, one user or more (see 38).
- **Why:** a resource belongs to its workspace, not to a person: it stays when its author leaves. Limits count by workspace, an audit reads the author.

## 6. Zero trust

- **Decision:** each request carries a short-lived token, and the server checks it on each request: signature, expiry, revocation. Then SpiceDB checks the exact permission. The right of a request is the SpiceDB permission AND the checks of the token. A long-lived credential is used only to get a token, never on a request.
- **Why:** no request is trusted because of where it comes from. A stolen token is valid for minutes, and it can carry fewer rights than its actor.
- **Not kept:** an actor in a request field or a trusted header (any client can claim any actor); long-lived API keys on each request.

## 7. Biscuit tokens

- **Decision:** the tokens are Biscuits, signed with an Ed25519 root key (`SCYLLA_TOKEN_PRIVATE_KEY`). The first block holds `actor(id, kind)`, `expires(unix)` and a time check. The default lifetime is 10 minutes. Each Datalog run on a token has at most 100 ms, and a query of the claims that fails refuses the token: the default limit of Biscuit (1 ms) failed on a busy machine, and an empty answer would hide the session of a token. The key id is in each token, and `SCYLLA_TOKEN_PUBLIC_KEYS` keeps older public keys valid after a rotation. `token revoke` revokes a token and each token made from it.
- **Why:** the check is offline (no call to a token server). A holder can attenuate a token offline (`check if operation("scylla.projects.v1.ProjectService/ListProjects")`) before it gives it to a step of a pipeline. Only the first block can name the actor, so a later block cannot change it.
- **Not kept:** JWT (no offline attenuation); opaque tokens in a table (a database read for each request). Biscuit 6.0.0 needs its `datalog-macro` feature to compile, and that feature brings `proc-macro-error2`, which gives a future-compatibility warning from upstream.

## 8. How each actor gets a token

- **Decision:** an App signs a short assertion (App id, key id, audience `scylla`, expiry of at most 2 minutes, nonce) with its Ed25519 private key: `ExchangeAppAssertion` (see 60). Its token is bound to its key: the first block has `key(<id>)`, and the gate refuses the token when the key is revoked or the App is deleted. A person signs in with a password (`AccountService.SignIn`), with an identity provider in a browser (`/auth/<slug>/start`, see 35), or with the OIDC ID token of a native client (`ExchangeIdToken`, issuer, audience, expiry and a JWKS signature checked, no HMAC). Each sign-in of a person opens a session (see 34). The CLI `token create` signs a token for a first admin.
- **Why:** an App keeps its private key, and the server keeps only the public key. The nonce table stops a replay. A person can use the identity provider of the company, or an account of Scylla (see 33).
- **Not kept:** a shared secret for the Apps.

## 9. Opaque ids

- **Decision:** `Id<T>` holds 128 bits, stored in a Postgres `uuid` column. Only `codec.rs` knows the text form and how to make a new id (UUIDv7 today).
- **Why:** a change to ULID or another 128-bit format changes one file. The type parameter stops a project id where an actor id goes. UUIDv7 ids sort in creation order, so pages use the id.
- **Not kept:** a format per entity (two text forms in one API); text ids in the database.

## 10. One proto id message

- **Decision:** all ids use `scylla.common.v1.Id { string value }`. The field name tells which entity. One generic `FromProto` and `ToProto` impl serves each `Id<T>`.
- **Why:** one parse and one error for all ids, no code for a new id kind. Typed id messages give no safety to a TypeScript client (same shape, same type), and the Rust domain keeps the typed ids.
- **Not kept:** one message per id kind; a nested `Uuid` message inside each id (two levels for clients).

## 11. Keyset pagination

- **Decision:** `PageRequest { size, token }` and `PageResponse { next_token }` in `scylla.common.v1`. The token is the last id, or the last name for `ListSecrets` (see 57). The store reads one row more than the page size. `ListAccess` has a token of its own, with the cursor of SpiceDB (see 51).
- **Why:** a page stays correct when rows change, and its cost does not grow with its position.

## 12. Errors

- **Decision:** one `scylla_core::Error` for the core and the edition routes. A bad field gives `INVALID_ARGUMENT` with a `google.rpc.BadRequest` that names the field. A refusal gives `FAILED_PRECONDITION` with a `google.rpc.ErrorInfo` (`reason`, `domain = scylla`, numbers and ids in `metadata`). Other errors give `INTERNAL` and go to the log.
- **Why:** a client reads codes and details, not messages, and each edition maps errors in the same way.

## 13. Crates

- **Decision:** `scylla-macros` (the `authz!` procedural macro), `scylla-domain` (pure types), `scylla-extension` (the contract), `scylla-proto` (generated code), `scylla-core`, `scylla-testkit`, `scylla-ce`.
- **Why:** the Enterprise repository needs the domain types and the contract without the core internals. Pure types compile in parallel with sqlx and tonic. `protoc` runs only on a proto change. `scylla-proto` gives its proto folder to the Enterprise build script with `links` metadata, so a Git dependency works. A procedural macro must be in its own crate, and `scylla-domain` gives it as `scylla_domain::authz!`.

## 14. Command line and settings

- **Decision:** `clap` (derive and `env`). Each setting is a flag and an environment variable, with a default. Commands: `serve` (the default) and `migrate`.
- **Why:** a standard tool gives help, checks and errors for free. A deploy runs `migrate` as one job before the servers, so servers never race to migrate. `serve` checks at start that each migration is applied.

## 15. Server for production

- **Decision:** graceful shutdown on SIGTERM and Ctrl+C, the standard `grpc.health.v1` service (it gives `NOT_SERVING` when the stop starts), one log line for each call (see 59), a request timeout, pool limits and a Postgres `statement_timeout`. The request timeout is longer than the statement timeout.
- **Why:** Kubernetes and Docker stop a pod with SIGTERM and probe its health. A slow statement fails in Postgres first and frees its locks. A client error is an `INFO` line, not a server failure.

## 16. Tests

- **Decision:** black-box gRPC tests first, one test binary per app with one module per feature, `// given`, `// when`, `// then`. Unit tests only for what the API cannot show.
- **Why:** the API is the contract. One binary links one time. The same server code runs in tests and in production.

## 17. Comments

- **Decision:** one `//!` line per file and a short `///` on each item, checked by the compiler. A long function body has steps: a blank line between two steps, and one `// Step.` line at the head of each step. No reasons in the code: they go here.
- **Why:** each item explains itself in the IDE and in `cargo doc`. A long function reads as a list of steps, and the code of a step tells how. The code stays short.
- **Not kept:** no comment in a body (a long function was hard to read); a comment on each line (noise that gets old).

## 18. Offline SQL data

- **Decision:** `.sqlx/` is in the repository.
- **Why:** CI builds with no database (`SQLX_OFFLINE=true`), and an offline Enterprise build compiles the core with this folder.

## 19. SpiceDB permissions

- **Decision:** SpiceDB holds the roles, in Postgres (its own database). The subject is always `actor`, so the actor kinds stay open. A workspace has the roles `admin`, `member` and `viewer`, with the groups `manage`, `work` and `read`. A project has the roles `admin`, `editor` and `viewer`, with the groups `delete`, `edit` and `view`. Each route has its own permission (see 28). Each plugin registers the model of its types (`EditionBuilder::authz`, see 25), and `migrate` writes the full schema.
- **Why:** roles and sharing are relations, not code. An edition adds its definitions with no change to the core. The owners of the workspaces are not in SpiceDB (see 29).
- **Not kept:** permission checks in SQL in each feature.

## 20. Consistency between Postgres and SpiceDB

- **Decision:** no write goes to the two stores. A creation or a delete changes Postgres only. A grant changes SpiceDB only. After a delete, the server removes the roles on the object, and logs a failure. An acceptance locks the row of its open invitation, writes the role, then marks the invitation, in one Postgres transaction (see 52): a retry after a failed commit writes the same role again with no harm. Each check that reaches SpiceDB is fully consistent.
- **Why:** a commit can fail in more than one way, and its result can even be unknown. With one store for each write, no undo is necessary. A grant on a deleted object reaches nothing, because each route reads the object from Postgres first, and ids are never used again. SpiceDB can answer from a cache up to 5 seconds old: a check just after a grant would give a false refusal, so correctness comes first. A ZedToken can make a check faster later (`Check::at_least_as_fresh`).
- **Not kept:** the owner written to SpiceDB before the commit, and deleted again after a failed commit (an unknown commit result leaves an owner with no right); a transactional outbox (a worker, a refusal just after a create, and one write for each resource).

## 21. An unknown resource gives `PERMISSION_DENIED`

- **Decision:** a route on an unknown object gives the same answer as a route without the permission. `GetWorkspace`, `UpdateWorkspace`, `GetProject`, `UpdateProject`, `DeleteProject`, the routes of `SecretService`, `Grant`, `Revoke` and `ListAccess` read the object from Postgres first: no row gives `AccessError::denied(&caller, &check)`, the refusal of the gate, with the same message. A route on an unknown workspace fails its check, because no owner and no role exist. `GetWorkspace` with a slug gives `PERMISSION_DENIED` for an unknown slug and for a slug that the caller cannot read, but a slug is public (see 48). `CheckPermissions` gives `false` for each permission on an unknown object (see 50). The account routes give the same answer for a known and an unknown email (see 33). A refusal on a secret names the secret, not its project (see 57).
- **Why:** a caller does not learn which ids or emails exist.

## 22. gRPC-Web

- **Decision:** the server accepts HTTP/1.1 and gRPC-Web (`tonic-web`) on the same port as gRPC. CORS allows only the origins of `SCYLLA_CORS_ORIGINS`, with the gRPC headers exposed.
- **Why:** a browser calls the API with no proxy. An empty list allows no web origin.

## 23. TLS in the server

- **Decision:** `SCYLLA_TLS_CERT` and `SCYLLA_TLS_KEY` turn on TLS (rustls with ring). Clap requires the two together. The process installs ring as its only crypto provider (`crypto::install`), for tonic and for the HTTP client of OIDC.
- **Why:** a deploy with no proxy can still encrypt. ring builds with no extra tool on Windows, Linux and macOS.

## 24. Tools

- **Decision:** the latest version of each tool and crate. The recipes call `cargo sqlx`. `scylla-protos` calls `buf`.
- **Why:** one known version for each tool, with the latest fixes. The README gives the install lines.


## 25. A typed permission model

- **Decision:** the procedural macro `authz!` declares each SpiceDB definition next to its Rust type, in the SpiceDB schema language. It implements `Resource` and `Model` for the type, and makes one constant for each name: `Project::DELETE` is a `Permission<Project>`, `Project::VIEWER` is a `Relation<Project, Actor>`. `Permission::on(id)` and `Relation::of(object, subject)` take typed ids, and only they make a `Check` or a `Relationship`. `EditionBuilder::authz::<T>()` adds the part of a type, and the edition writes the schema from the parts. `authz! { extend Project as ProjectAudit { ... } }` adds relations and permissions to a definition of another plugin.
- **Why:** one source for the schema and the code. The compiler stops a wrong name, a wrong id type, and a wrong name in a permission expression (an arrow is checked on the subject type). SpiceDB checks the full schema each time a test writes it. An edition adds objects, relations and permissions with no change to the core.
- **Not kept:** schema text and names as text (no check before run time); a `macro_rules!` macro (no constants in upper case, no check of the expressions); a typed SpiceDB client from another crate (it replaces the official client, and no crate is a standard); an extension that changes an existing permission (an extension only adds, so the core rules stay true).

## 26. The operation is the gRPC method

- **Decision:** `OperationLayer` adds the gRPC method of each request (`scylla.projects.v1.ProjectService/CreateProject`) to the request. `Gate::caller` gives it to the token check as `operation`.
- **Why:** no name to write and keep in each handler, and the same name that the client sees. A token can allow one service with a prefix: `check if operation($op), $op.starts_with("scylla.projects.v1.ProjectService/")`.
- **Not kept:** a name in each handler (`projects.create`): a handler can forget it or write a wrong one.

## 27. One SpiceDB store for each test

- **Decision:** the tests use `spicedb serve-testing` (`spicedb-test`, port 55052). Each `TestApp` uses a new key, and serve-testing gives an empty store in memory to each key. `.cargo/config.toml` runs the tests on 8 threads.
- **Why:** the tests run in parallel with different schemas (an edition extends a definition) and with no shared relationships, as `sqlx::test` gives a new database to each test. The dev SpiceDB keeps only dev data. `sqlx::test` shares 20 database connections between the tests that run at the same time. With 16 threads, a test waited 30 seconds for a connection.
- **Not kept:** the dev SpiceDB for the tests: the schema write of one test changes the schema of all the tests, and the relationships stay after the tests.

## 28. One permission for each route

- **Decision:** each route that verifies a token checks its own permission: the RPC name in snake case, on the object of the route. `CreateProject` checks `create_project` on the workspace. `DeleteProject` checks `delete_project` on the project and on its workspace. A route of the caller itself checks its permission on the caller: `ListProjects`, `ListWorkspaces`, `CreateWorkspace`, `AcceptInvitation`, `CheckPermissions` and the routes of `ProfileService`. A route on the whole instance checks its permission on the platform object (see 42): the routes of `UserAdminService`. A route permission uses a group: `manage`, `work`, `read` in a workspace, `delete`, `edit`, `view` on a project, `nil` on the caller and on the platform. A feature adds the permissions of its routes on the workspace with `extend Workspace as <Feature>Holder`, on the caller with `extend Actor as <Feature>Caller`, on the platform with `extend Platform as <Feature>Holder`, and on the object only when one object can be shared. The gate refuses a check of a permission that is not the route permission. After the route, the server refuses a success when the route verified a token and passed no check of its route permission: it answers `PERMISSION_DENIED` and logs an error.
- **Why:** a role can give one route and not the others: a quota reader reads quotas and creates nothing. Groups keep the common case short, and a new role changes the schema, not the code. A route that forgets its check, or that checks a group, fails in the tests of its success.
- **Not kept:** checks of groups in the routes (a new role gives all the routes of the group, or a change of code); a list of route permissions in a table (a second source next to the schema); a stop before the route runs when a check is missing (the server does not know the object of the route before the route reads the request). A route that must also check the permission of another route needs a new decision.

## 29. The owners of a workspace in Postgres, the roles in SpiceDB

- **Decision:** Postgres holds the containers and their owners: `workspace_owners`, and the `workspace_id` of each resource. SpiceDB holds only the roles that a person gives on purpose: in a workspace, or on one object. The gate finds the rights of a request in this order: the caller is the object itself (a route on the caller), an instance admin on the platform object (see 42), or an owner of the workspace, with no SpiceDB call; else one `CheckBulkPermissions` call asks for the route permission on the object and on its workspace. A role in a workspace goes down to all that is in it. A check of an object in a workspace names it: `Project::DELETE_PROJECT.on(id).within(workspace)`.
- **Why:** a creation or a delete is one Postgres transaction, with no write to SpiceDB and no undo. The owners of a workspace never lose access, even with SpiceDB down. SpiceDB stores only the roles, not one relationship for each resource. The workspace is business data: lists, quotas under concurrency, foreign keys and hooks read it in SQL. A role on one object stays possible, for precise sharing.
- **Not kept:** the container in SpiceDB (a SpiceDB write at each creation, no sorted lists, no quota lock, no foreign key); an owner on each resource (see 32).

## 30. Roles given with `AccessService`

- **Decision:** `AccessService` gives a role with `Grant`, takes it back with `Revoke`, lists the access to an object with `ListAccess` (see 51), and tells a caller its permissions with `CheckPermissions` (see 50). A request names an object (`kind` and `id`), a role and an actor. The edition has a registry of the kinds and of the roles that a person can give: a plugin registers a kind with `.grants(AccessRoutes { grant: Project::GRANT, revoke: Project::REVOKE, list_access: Project::LIST_ACCESS }, service::find_workspace)`, then each role with `.role(Project::VIEWER)`. The search for the workspace is required: it finds the workspace of an object, the workspace itself for a workspace, and tells that an object does not exist. An edition adds a role to a core kind, for example `.role(QuotaHolder::QUOTA_READER)`. The route permissions are `grant`, `revoke` and `list_access` on the object, with its workspace from Postgres. `grant` and `revoke` are `admin`: only the owners of the workspace and the direct admins give or take back roles. `Grant` needs an actor that exists, and an agent of the workspace of the object (see 54). A `Revoke` of a role that the actor does not have is not an error. An unknown kind, a bad id and a name that is not a registered role are request errors.
- **Why:** one service for all kinds, and only the roles of the registry: a permission, or a relation that a plugin did not register, cannot be written. The plugin that owns a kind tells how to find its workspace, so the check is the same as on the other routes. A role that stays on a deleted workspace reaches nothing, because the search reads the workspace from Postgres first.
- **Not kept:** a `Grant` RPC in each service (the same code in each feature); a grant written as text (the typed `Relation` gives the kind and the name).

## 31. A list shows what the caller can see

- **Decision:** `ListProjects` returns the projects of the workspaces that the caller owns, of the workspaces where it has a role that lists them, and each project shared with it. `ListWorkspaces` returns the workspaces that the caller owns and the workspaces where it has a role. Postgres gives the owned workspaces. SpiceDB reverse lookups (`LookupResources`, fully consistent) give the others. `workspace_id` is a filter: it causes no refusal. If a lookup fails, the list shows the owned ones only, and the server logs a warning.
- **Why:** a project shared with an actor must be in its list, or the share is of no use. The owner path stays in Postgres, so an owner lists its projects with no SpiceDB. With a share of one project, a caller can see some projects of a workspace and not the others: the filter returns the visible ones.
- **Not kept:** an error when SpiceDB does not answer (the owner path does not need SpiceDB). A caller with very many roles makes one long lookup: a cursor on the lookup is a later change.

## 32. Workspaces

- **Decision:** a workspace is the top-level container: `workspaces (id, name, slug, created_at)`. Each project and each App is in one workspace. Its owners are users, in their own table (see 38). A new user gets a personal workspace, and becomes its owner, in the transaction of its creation. A user creates more workspaces with `CreateWorkspace`, and becomes their first owner. A workspace has a unique slug for the URLs (see 48). Its admins change its name and its slug, and its owners delete it when it is empty (see 49). A person joins a workspace by an invitation (see 37) or a role from `Grant`.
- **Why:** a resource belongs to its team, not to a person. The owners keep a root that never loses access. Quotas, lists and later the SSO of a company have one natural scope. The name follows Slack and Linear.
- **Not kept:** an owner on each resource (the owner leaves, the resource stays); folders between the workspace and the projects (a later layer: the gate chain can grow); the name "organization".

## 38. The owners of a workspace are a relation

- **Decision:** `workspace_owners (workspace_id, user_id, created_at)` holds the owners, with the primary key `(workspace_id, user_id)`. A workspace has one owner or more. `WorkspaceService` changes them with `AddOwner` and `RemoveOwner`, and reads them with `ListOwners`. Only an owner changes the owners: `add_owner` and `remove_owner` are `nil` in the schema, so no role gives them. `ListOwners` needs `read`. An owner can take out another owner or itself. `RemoveOwner` locks the row of the workspace, deletes, counts, and refuses with `LAST_OWNER` when no owner stays. A second `AddOwner` of the same user changes nothing, and so does a `RemoveOwner` of a user that is not an owner. Only a user can be an owner: an agent or an unknown id gives `NOT_FOUND`.
- **Why:** an owner is a relation between a person and a workspace, not an attribute of the workspace. A column gives a workspace to one person only, and a team must not depend on one person. The owners stay in Postgres for the reasons of 29: a creation is one transaction, and the owners keep access with SpiceDB down. The last-owner rule holds under concurrent removals for the reason of the Enterprise project limit: each removal takes the lock of the workspace first, and in READ COMMITTED the count after the lock sees each removal that a previous holder committed. An addition does not take the lock: it can only cause a refusal, never a workspace with no owner. Without the lock, `two_owners_cannot_take_each_other_out` failed on 3 runs of 3.
- **Not kept:** `workspaces.owner_id` (one person only); an `owner` relation in SpiceDB (a SpiceDB write at each creation, see 29); `owner` as a role of `AccessService` (two stores behind one API); a group or an agent as an owner (a later change: a table of its own, or a principal type).

## 33. Accounts in Scylla

- **Decision:** Scylla keeps its own users: `users` (profile, optional handle, and status `pending`, `active` or `disabled`), `user_emails`, `passwords` (Argon2id, off the async threads), and `external_identities` (provider and subject). One user has many ways to sign in. `SignUp` follows `SCYLLA_SIGN_UP_MODE`: `open`, `invite_only` (the default) or `closed`. The CLI `user create` makes a first user, and `--admin` makes it an instance admin (see 42). A sign-up sends a one-time link that verifies the email, and an invitation link verifies it too. A password has 8 to 128 characters and no other rule. `SignIn` takes an identifier: a text with an `@` is an email, else a handle (see 41). An identifier that is not valid, an unknown identifier and a wrong password get the same answer. A known email at sign-up gets the same answer, and its owner gets a mail. 5 failures lock the account for a time that grows to one hour, and a failure while the account is locked does not count. `RequestPasswordReset` answers first, then a task makes the link and sends it: the time of the answer does not tell if the email has an account. The task sends at most one reset link each 60 seconds for one account, with no error, and a new link stops the older ones. A reset link works one hour and closes each session. A change of email follows the same rules: `RequestEmailChange` needs the current password if the user has one, answers first, and a task sends a link to the new email, at most one each 60 seconds for one user and for one email, and none to an email that an account uses. `ConfirmEmailChange`, with the token of the link and the session of the same user, makes the new email the primary verified email, stops each other open link of the user, and the old email gets a notice. A new email from `UpdateUser` also stops each open link. A link works only while its email is an email of its user, except the link to a new email. The database keeps only the hashes of the one-time tokens.
- **Why:** a self-hosted install needs accounts with no other service, and a company can still use its identity provider (see 35). The rules come from OWASP and NIST: no enumeration, slow hashes, short links, and a lock that does not tell which accounts exist. NIST SP 800-63B asks for 8 characters or more with a second factor. The lock after 5 failures stops the online guess of a short password, and the users of the old product and its web app use 8. The cooldown stops a flood of mails to one person, and the task after the answer keeps the same time for each email. After a change of email, a person who still reads the old mailbox must not use a link that went there, for example to reset the password. The current password before a change of email stops a person with a stolen session. The limit for one email stops a flood of mails to a person that does not have an account. A failure while the account is locked does not make the lock longer, and the length stays at one hour at most, so the time of the lock cannot overflow.
- **Not kept:** an identity provider as the only way (one more heavy service for each install); a headless identity service next to Scylla (one more service and database); 15 characters as the minimum (NIST asks for it when the password is the only factor, but the users of the old product have shorter passwords); a mail sent in the request (a known email gives a slower answer). Not in this change: MFA, passkeys, magic links, personal tokens, a check against breached passwords, and a limit for each IP address.

## 34. Sessions

- **Decision:** each sign-in of a person opens a session: `sessions (id, user_id, refresh_hash, methods, user_agent, ip_address, expires_at, revoked_at)`, for `SCYLLA_SESSION_TTL_DAYS` (30). The refresh token is `<session id>.<secret>`, and the database keeps the hash of the secret. `Refresh` gives a new token and a new secret, and the old secret stops. An old secret that comes again closes the session. Each access token of a person names its session (`session(id)` in the first block). The gate refuses a token of a closed or expired session, or of a disabled or deleted user, in the query of the revocations. A session keeps the user agent and the IP address of the sign-in (see 45). A browser keeps the refresh token in an HttpOnly cookie `scylla_session` (`SameSite=Lax`, `Secure` with HTTPS), and a refresh with the cookie needs an `Origin` of `SCYLLA_CORS_ORIGINS`. `SignOut`, `RevokeSession`, `RevokeOtherSessions`, `RevokeUserSessions`, a disabled account, and a reset or a change of the password close sessions at once.
- **Why:** a short access token keeps the offline check of Biscuit (see 7), and the session gives a way to stop a person at once. The rotation and the reuse check find a stolen refresh token. A cookie keeps the refresh token away from the scripts of the page.
- **Not kept:** long-lived access tokens (no stop before their end); a refresh token in the storage of the browser (the scripts of the page can read it). Two tabs that refresh at the same time can close the session: a grace time for the old secret is a later change.

## 35. Sign-in with an identity provider

- **Decision:** the identity providers are rows of `identity_providers`, with a kind and its settings in JSON: `oidc` (any OpenID Connect provider) and `github` (OAuth 2 and the API, for GitHub and GitHub Enterprise Server). The CLI adds and changes them (`provider add-oidc`, `provider add-github`), and their client secrets are encrypted with `SCYLLA_SECRET_KEY` (XChaCha20-Poly1305, see 58). A browser opens `/auth/<slug>/start`: the server stores the sign-in for 10 minutes with a state, a PKCE verifier and a nonce, sets the cookie `scylla_flow`, and sends the browser to the provider. `/auth/<slug>/callback` takes the sign-in of the state one time, needs the cookie of the same browser, exchanges the code, checks the ID token and its nonce, opens a session in the session cookie, and goes back to the web app. A return address must be in the web app. These HTTP routes are next to the gRPC routes, outside the gRPC-Web layer, which refuses other HTTP/1.1 requests. A native client gives an ID token to `ExchangeIdToken`, and its issuer names the provider. A new identity makes a user only if the provider allows sign-up, the sign-up mode allows it (an open invitation for the email in `invite_only`), and the provider gives a verified email that no account has.
- **Why:** an operator adds a provider with no new release, and a kind is code in one place. The state, the PKCE verifier, the nonce and the browser cookie stop a forged callback, a stolen code, and a sign-in in the browser of another person. The server keeps the client secret, which the browser must never see.
- **Not kept:** the provider in the settings of the server (one provider only, and a restart for each change); a trait of the extension crate for the kinds (it comes with the first EE kind, SAML).

## 36. No automatic link by email

- **Decision:** an identity of a provider is never linked to an account because the emails match. A new identity with the email of an account is refused (`EMAIL_IN_USE`). The person signs in to the account first, then opens `/auth/<slug>/start?link=true` with its session cookie, and the callback needs the session of the same user. An identity of another user is refused (`IDENTITY_IN_USE`). `UnlinkIdentity` cannot remove the last way to sign in.
- **Why:** a provider can give an email that the person does not own. A link on the email alone gives the account to the person who controls that provider.
- **Not kept:** an automatic link for a verified email (a provider can verify badly); an automatic link for a domain that a workspace owns (a later EE feature, with the proof of the domain).

## 37. Invitations and mails

- **Decision:** an admin of a workspace invites an email with a role (`CreateInvitation`). The link goes to that email only, and works 7 days. The admin lists, revokes and sends again the open invitations (see 52). A user with this verified email accepts it (`AcceptInvitation`), or signs up with it in the mode `invite_only`. The mails go through the `Mailer` trait of the extension crate: SMTP (`SCYLLA_SMTP_URL`, lettre with rustls), or with no SMTP, a log of the recipient and the subject, never of the link. Each mail has a text body and an HTML body (see 47), and each link has its token in the fragment (see 46). The dev compose has Mailpit (SMTP 51025, web 51080). A failed mail goes to the log, and the request does not fail.
- **Why:** a link to an email proves that email, so the invited person needs no other check. An edition or a test can give its own mailer.
- **Not kept:** the link in the answer of `CreateInvitation` (the admin could use it); a mail queue (a later change, if mails fail often).

## 39. No compatibility code

- **Decision:** Scylla has no deployed database and no client of an old version, so the code keeps no trace of a previous design. A proto removes a field or an RPC with no `reserved` line and no deprecated mark, and the fields of a message have the numbers 1 to n. The `buf.yaml` of `scylla-protos` has no breaking rules. A migration has only `CREATE` statements, one file for each feature: a change of a table changes its `CREATE TABLE`, and `just db-reset` creates the dev database again. `build.rs` makes Cargo rebuild `scylla-core` and `scylla-ee` when a migration changes, because `sqlx::migrate!` embeds the files.
- **Why:** an upgrade path costs code, tests and reading time, and nothing uses it before a first release. The clean migrations give the same tables, columns, constraints and indexes as the old chain: a comparison of the two catalogs found no difference.
- **Not kept:** forward migrations with data moves (they stay in the history for a design that is gone); `reserved` fields (no old client reads them). After a first release, this decision changes: from then on, a change is a new migration.

## 40. The code is grouped by subject

- **Decision:** each crate groups its code by subject: `identity` (accounts, instance admins, sessions, providers, tokens, actors, agents), `tenancy` (workspaces and their owners, invitations, roles), `projects`, and `platform` (the platform object, capabilities). `scylla-domain` has `kernel/` (ids, names, pages, kinds, errors, with each type at the crate root), `authz/`, `identity/`, `tenancy/`, `platform.rs`, and `projects.rs` with `projects/secrets.rs`. `scylla-core` has only `lib.rs`, `app.rs`, `config.rs` and `error.rs` at its root, then `access/`, `api/` (server, layers, proto conversions), `cli/`, `infra/` (database, mails, secrets, TLS) and `features/<subject>/<feature>/`. The feature with the name of its subject stays at the level of the subject (`features/projects/`, `projects.rs`), and the other features of that subject go below it (`features/projects/secrets/`, `projects/secrets.rs`). The testkit has one file for each subject, or a folder when a subject grows, and the API tests one folder for each subject.
- **Why:** a flat folder mixed roles (kernel types and entities, wiring and adapters) and grew with each feature. A subject keeps its features side by side: the account, session, provider and token code changes together. The same split in the domain, the core, the testkit and the tests shows where a new file goes. A module with the name of its parent (`projects/projects.rs`) is a clippy error (`module_inception`), so the feature with the name of its subject does not go in a folder of its own.
- **Not kept:** folders by role only, with the 11 features flat in `features/` (the pile-up comes back); one crate for each subject (the compiler would enforce the borders, but with more crates for the Enterprise build to pin and one migration ledger for each crate). A subject that grows can become a crate later: its folder is already its border.

## 41. Handles

- **Decision:** a user can have one handle: a short name, unique, in `users.handle` with a unique constraint. A handle has 2 to 39 characters: lower case letters, digits, dots, dashes and underscores, and it starts with a letter or a digit (`^[a-z0-9][a-z0-9._-]{1,38}$`). The server trims it and makes it lower case. A handle has no `@`, so `SignIn` reads a text with an `@` as an email and the other texts as a handle. `UpdateProfile` and `UpdateUser` set it, an empty text removes it, and a handle of another user gives `HANDLE_IN_USE`. A new user has no handle, except a user of `CreateUser` or `user create --handle`.
- **Why:** the users of the old product sign in with a short name, and a short name is easy to type and to show. The rule of the characters keeps a handle safe in a URL and in a mention, and the length follows GitHub.
- **Not kept:** a handle made from the email at sign-up (retry loops for a name that nobody chose); a required handle (one more step at sign-up); a handle in any case (two users that look the same).

## 42. Instance admins and the platform object

- **Decision:** `instance_admins (user_id, created_at)` holds the admins of the instance, one row for each admin user. The authz definition `platform` (`scylla_domain::platform::Platform`) has one object, `Platform::ID`, and the routes on the whole instance check their permission on it. These permissions are `nil`: no role gives them. The gate passes an instance admin on the platform object from Postgres, with no SpiceDB call, as it passes an owner on a workspace (see 29). `user create --admin`, `user admin grant <id>` and `user admin revoke <id>` change the admins from the command line, and `GrantInstanceAdmin` and `RevokeInstanceAdmin` from the API. The instance keeps one active admin or more: a change that takes the last active admin out (a revoke, a disabled account, a deletion) gives `LAST_ADMIN`. The change locks the rows of `instance_admins` first, then reads the states of their accounts in a new statement, so two changes at the same time run one after the other, and the second sees the first. A read of the states in the statement of the lock sees the states before the lock: two admins that disabled each other at the same time both passed. `GetMe` tells if the caller is an instance admin.
- **Why:** an operator needs a person that manages the users with no access to the database. A relation table follows the owners of a workspace (see 38): the right stays in Postgres, with SpiceDB down too, and a creation needs no SpiceDB write. One object for the instance keeps the rule of decision 28: each route checks its own permission on an object.
- **Not kept:** a flag column in `users` (a right is a relation, not an attribute); an `admin` role in SpiceDB (a second store for a right that Postgres must also read for the rule of the last admin); the actor itself as the object of the admin routes (each user would pass on itself).

## 43. The console of the users

- **Decision:** `UserAdminService` (package `scylla.accounts.v1`) is the console of the instance admins: `ListUsers` (keyset pages, a filter on the email, the handle and the display name), `GetUser`, `CreateUser` (an active user with a verified email and a password), `UpdateUser` (display name, handle, and a new primary email, verified, that stops each open link of the user), `SetUserStatus` (`active` or `disabled`, never on the caller: `SELF_NOT_ALLOWED`; a disabled user loses each session), `DeleteUser` (the rules of 44, never on the caller), `SendPasswordReset` (the rules of the reset in 33), `ListUserSessions`, `RevokeUserSessions`, `GrantInstanceAdmin` and `RevokeInstanceAdmin`. Each route checks its permission on the platform object (see 42). An unknown user gives `NOT_FOUND`.
- **Why:** an operator lists, creates, stops and removes accounts with no SQL. An instance admin can see each account, so `NOT_FOUND` tells it nothing new (see 21). A user who wants to delete its own account uses `ProfileService`, with its password.
- **Not kept:** a list of the roles of a user (the roles are in SpiceDB, and the console of the workspaces shows them); a version check on `UpdateUser` (the last change wins).

## 44. The deletion of an account

- **Decision:** `DeleteAccount` (with the current password if the user has one) and `DeleteUser` delete a user in one Postgres transaction: the row of `users`, and with it its emails, its password, its sessions, its identities, its one-time tokens and its admin row; and its owner rows in `workspace_owners`. The row of `actors` stays, so each `created_by` and `invited_by` stays valid, and `invitations.accepted_by` refers to `actors`. A workspace where the user is the only owner goes with the user if it is empty: no project, no agent, no other owner, and no role of another actor (a SpiceDB read of its relationships). Else the deletion stops with `LAST_OWNER`, and the `ErrorInfo` metadata `workspace_ids` names these workspaces. The last active instance admin stays (`LAST_ADMIN`). The transaction locks the user, the instance admins and the workspaces of the user, in this order. The lock of a workspace is the lock of `RemoveOwner` (see 38). After the lock, a workspace goes with the user only if the user is still its one owner: a removal of the user that a previous holder of the lock committed leaves the workspace to its other owner. After the commit, the server removes the relationships of the user as a subject (`Gate::delete_subject`) and of each deleted workspace (`Gate::delete_object`), and logs a failure. The gate refuses each token of an actor of kind `user` with no row in `users`.
- **Why:** a person can leave, and an admin can remove an account, with no SQL. A workspace with content belongs to a team: its last owner must give it to another owner first. A deleted actor would break the history of each resource that it made. The roles go after the commit for the reasons of 20: a role of a deleted user reaches nothing, because its tokens stop.
- **Not kept:** a soft delete (a second state next to `disabled`); the deletion of a workspace with content (data loss with no undo); a transfer of the workspaces in the same call (a later change, with a choice of the new owner).

## 45. The IP address of a session

- **Decision:** `sessions.ip_address` (`inet`) keeps the IP address of the client at the sign-in: the peer address of the connection. With `SCYLLA_TRUST_FORWARDED_HEADERS=true`, it is the last address of `X-Forwarded-For`: the address that the proxy adds. A value that is not an address gives the peer address. `ListSessions` and `ListUserSessions` show it with the user agent.
- **Why:** a person and an admin find an unknown session by its place. Behind a proxy, the peer address is the proxy, so the operator turns on the header. A client can write any `X-Forwarded-For`, so the server reads it only when the operator says that a proxy adds to it, and it reads only the address that this proxy adds: the addresses before it come from the client.
- **Not kept:** the address of the last refresh (one more write for each refresh); the first address of `X-Forwarded-For` (the client writes it, so a client can show any address); a setting for a number of proxies (one proxy is the common case, a later change).

## 46. The token of a link in the fragment

- **Decision:** each mail link puts its one-time token in the fragment of the URL: `<app_url>/<page>#token=<token>`, for `verify-email`, `reset-password`, `accept-invitation` and `change-email`. `AccountSettings::link` makes each link.
- **Why:** a browser does not send the fragment to a server, so the token is not in the logs of a proxy or of the server of the web app, and not in a `Referer` header. The web app reads the fragment and removes it from the history.
- **Not kept:** the token in the query (`?token=`): it goes to each server on the path.

## 47. HTML mails

- **Decision:** a `Mail` of the extension crate has a text body and an HTML body with the same content. The SMTP mailer sends the two as `multipart/alternative`. The log mailer logs only the recipient and the subject. The account mails (check of an email, reset, a sign-up with a known email, an invitation, the link to a new email, and the notice to the old email) come from one layout (`Letter`): paragraphs, a button with the link, and the link as text. The HTML has inline styles only, and each value is escaped.
- **Why:** a mail client shows a button, and a client with no HTML shows the text. Inline styles work in each mail client. The escape stops markup in a name, for example the name of a workspace in an invitation.
- **Not kept:** HTML only (some clients and filters need the text); a template engine (six short mails do not need one); translated mails (a later change, with the language of the user).

## 48. The slug of a workspace

- **Decision:** each workspace has a slug for the URLs: `workspaces.slug`, unique, with a check of its form in the table. A slug has 2 to 39 lower case letters, digits or dashes, and starts and ends with a letter or a digit (`^[a-z0-9][a-z0-9-]{0,37}[a-z0-9]$`). The server trims it and makes it lower case. `CreateWorkspace` takes an optional slug: a slug in use gives `SLUG_IN_USE`. With no slug, the server makes one from the name (`Slug::derive`: the letters in ASCII with `deunicode`, the digits, one dash for each run of other characters, cut to 39 characters), and a slug in use gets the first free suffix: `-2`, `-3` and on. A name with fewer than two letters and digits gives `workspace`. The personal workspace of a new user takes the slug of its handle, else of its display name, with the same suffix. `UpdateWorkspace` changes the slug. A reserved name is not a slug (`ReservedSlug`, `INVALID_ARGUMENT`), and a derived slug that is a reserved name takes the suffix path: `Settings` gives `settings-2`. The reserved names are the top-level routes of the web apps (`login`, `sign-up`, `verify-email`, `forgot-password`, `reset-password`, `accept-invitation`, `change-email`, `account` in `scylla-web`, `register`, `invite`, `feedback` in `scylla-cloud-web`), the routes in a workspace (`projects`, `members`, `users`, `extensions`), the HTTP routes of the server (`auth`, `webhooks`), and names for later routes (`admin`, `api`, `assets`, `health`, `logout`, `metrics`, `new`, `settings`, `sign-in`, `static`, `workspaces`). `GetWorkspace` takes an id or a slug (a `oneof`). Slugs are public: they are in the URLs, and `SLUG_IN_USE` tells that a slug exists. `GetWorkspace` still gives `PERMISSION_DENIED` for a slug that the caller cannot read, as for an unknown slug, and the refusal names the slug, not the id of the workspace.
- **Why:** a URL with a short name is easy to read and to share. The old product made the URL from the name, which is not unique, so two organizations could have the same URL. A workspace URL is `<app>/<slug>`, so a slug must not hide a route of the app or of the server. A handle can have dots and underscores, so the personal slug comes from the same derivation. A oneof keeps one route and one permission (`get_workspace`). A slug is not a secret, so the server does not hide which slugs exist.
- **Not kept:** the id in the URL (hard to read); a `GetWorkspaceBySlug` route (a second permission for the same read); a refusal of a derived slug in use (a person who creates "Team" must not choose a new name).

## 49. A workspace changes and goes

- **Decision:** `UpdateWorkspace` changes the name and the slug, with `update_workspace = manage`. `DeleteWorkspace` deletes a workspace, with `delete_workspace = nil`: only its owners pass, no role gives it. A workspace with a project or an agent stays: `WORKSPACE_NOT_EMPTY`. The delete is one transaction: it locks the row of the workspace, counts the projects and the agents in a new statement, then deletes the row, and its owners and invitations go with it (`ON DELETE CASCADE`). After the commit, the server removes the roles on the workspace (`Gate::delete_object`), and logs a failure. A workspace has no description and no active flag.
- **Why it holds under concurrency:** a project creation or an App creation inserts a row with a foreign key to the workspace, and the check of the key takes a key share lock on the row of the workspace. The lock of the delete (`FOR UPDATE`) conflicts with it. If the creation is first, the delete waits for its commit, and in READ COMMITTED the count after the lock sees the new row: `WORKSPACE_NOT_EMPTY`. If the delete is first, the creation waits, then its foreign key fails on the deleted row: `NOT_FOUND`. An owner addition or an invitation at the same time also fails on its foreign key with `NOT_FOUND` (`a_change_that_races_a_delete_finds_no_workspace`). The project limit of the Enterprise edition locks the same row first, so it waits in the same way. Without the lock, the count can miss a project that is not committed, and the delete then fails on the foreign key of `projects` with an internal error: `a_creation_cannot_slip_into_a_deleted_workspace` failed on 3 runs of 3.
- **Not kept:** the delete of the content with the workspace (data loss with no undo, see 44); a transfer of the content (a later change); an admin that deletes (an owner is the root of a workspace, see 38).

## 50. The permissions of a caller

- **Decision:** `AccessService.CheckPermissions(object, permissions)` tells, for each name, if the caller has the permission on the object. The object is a workspace, a project, another kind of the registry of `AccessService`, or the platform. A name must be a permission of the definition of the object (`Schema::permission`), and a request has at most 50 names: else `INVALID_ARGUMENT`. Groups are permissions too, but a client asks for the route permissions. The answer uses the rights of a route check (`Gate::permissions`): the actor itself, an instance admin on the platform, an owner of the workspace, else one `CheckBulkPermissions` call for each name on the object and on its workspace. An unknown object gives `false` for each name. The route checks only its own permission, `check_permissions = nil` on the caller, so each caller asks for itself. The answers are not route checks: the gate does not record them for the route rule (see 28), the token does not take part, and an answer never lets a route pass.
- **Why:** the web app shows or hides an action with `can()`, and one call answers for a page. A route check records its success for the route rule, so an answer that recorded a check would let a route with no check of its own pass. The answer tells the rights of the actor: an attenuated token can still be refused by a route that the answer allows.
- **Not kept:** a list of the roles of the caller that the client maps to permissions (the mapping would be a second model in the client); the checks of the token in the answer (the web app has a full token).

## 51. The list of the access to an object

- **Decision:** `AccessService.ListAccess(object)` lists the access to a workspace, a project, or another kind of the registry. For a workspace, its owners come first, from Postgres, in user id order, with the role `owner`. Then the roles on the object come from SpiceDB (`ReadRelationships` with a filter on the object and on the subjects of kind `actor`), in the order of SpiceDB. Each entry has the actor id, its kind, the display name and the handle of a user, and the role. The route permission is `list_access`: `read` on a workspace, so the members see the members, and `view` on a project. A role in the workspace gives `list_access` on each project of it. The pages use the cursor of SpiceDB: the token of a page is `owners.<user id>` or `roles.<cursor>`, and each read of SpiceDB has the same limit (101), because a cursor needs the same request each time. A page with fewer owners than its size takes the first roles. A token that the list did not make, or that SpiceDB refuses, is a request error. The list of a project has no owners and no roles of the workspace.
- **Why:** the members page of the web app needs the owners and the roles in one list. The roles stay in SpiceDB and the owners in Postgres (see 29), so nothing is copied. A cursor is the only way to page `ReadRelationships`.
- **Not kept:** a copy of the roles in Postgres (two stores for one fact); a read of all the roles for each page (its cost grows with the number of roles); the access that a project gets from its workspace (the list of the workspace gives it).

## 52. The open invitations

- **Decision:** `InvitationService` lists, revokes and sends again the open invitations: the invitations that nobody accepted, expired ones too. `ListInvitations`, `RevokeInvitation` and `ResendInvitation` check `list_invitations`, `revoke_invitation` and `resend_invitation` (`manage`) on the workspace of the request. An invitation that is not open in this workspace gives `NOT_FOUND`. A revoke deletes the row, so its link stops. A resend locks the row, makes a new token and a new expiry of 7 days, sets `sent_at`, and sends a mail: the old link stops. A second send in less than 60 seconds gives `RESEND_TOO_SOON` with `retry_after_seconds`. Postgres gives each time: `sent_at` and `expires_at` come from `now()` at the creation and at a resend, and the cooldown compares `sent_at` with `now()` in SQL. An email has one open invitation in a workspace or none: the unique index `invitations_one_open_idx (workspace_id, email) WHERE accepted_at IS NULL` holds it under concurrency, and a second `CreateInvitation` gives `INVITATION_PENDING`, expired or not: the admin uses `ResendInvitation`. An acceptance is one transaction: it locks the row of the open invitation (by the hash of the token of the link, or by its id for a sign-in with an identity provider), checks the verified email, writes the role, marks the invitation where `accepted_at IS NULL`, and commits. A revoke or a resend at the same time waits for it, then finds no open invitation (`NOT_FOUND`). If the revoke or the resend is first, the lock of the acceptance waits, and in READ COMMITTED the row is gone or has a new token: the link gets the answer of an unknown link. `an_accept_and_a_revoke_never_both_pass` and `an_accept_and_a_resend_never_both_pass` failed on each run before the lock.
- **Why:** an admin must see and stop the links that it sent, and send a link again when a mail is lost or a link expired. The request names the workspace, so the check needs no read of the invitation, and the caller already sees the invitations of the workspace: `NOT_FOUND` tells it nothing new. The cooldown stops a flood of mails to one person, and the admin sees why the send failed. One clock gives the same result on each server. With two open invitations of one email, a revoke of one would leave a link that works. A revoked or replaced link must give no role, even when the person opens it at the same time.
- **Not kept:** a status column (`revoked`): a revoked invitation has no use; a silent cooldown, as for the account mails (see 33): the caller is an admin, not an unknown person; batches, seats and the language of the mail (Enterprise).

## 53. Each refusal goes to the log

- **Decision:** each refusal of an access logs the event `access.refused` at `WARN`, with the actor and its kind, the operation (the gRPC method), the permission, the object, and the reason of a refusal that is not a missing right (`the token does not allow this operation`). `AccessError::denied(principal, check)` and `AccessError::refused` log it and make the answer. The gate uses them for a refusal of the token and of the rights, and a route uses them for an unknown object and for a rule of the route (only a user creates a workspace or accepts an invitation). The log of the server puts this event on the line of its call (see 59): the permission and the object are on the second line in the pretty format, and they are fields of the `rpc` event in JSON. The line of the call is a `WARN` line. A refusal with no call, for example in a test, has its own line. A check of a permission that is not the route permission stays an `ERROR`: it is a bug of the route. There is no audit table.
- **Why:** an operator finds an attack or a wrong role in the logs. Nothing read the audit table of the old product, and a row for each check cost a write on each request. One line for each call keeps all the facts of the refusal, with no second line that only the time links to its call.
- **Not kept:** an audit table; a line for each passed check (the line of the call has the route and its code); a line of its own for each refusal (two lines for one call).

## 54. An App gets roles only in its workspace

- **Decision:** `Grant` refuses a role for an App on an object of another workspace: `ACTOR_OUTSIDE_WORKSPACE`. The workspace of the object comes from the registry of `AccessService` (the workspace itself for a workspace). An actor that is not an App gets roles in each workspace. The check comes after the route check, so a caller with no right learns nothing about the agent.
- **Why:** an App is a machine of one workspace. A role in another workspace would let a machine of one team act for another team. The old product had the same rule.
- **Not kept:** a check in SpiceDB (the workspace of an App is in Postgres); a refusal of each actor outside the workspace (a person can work in many workspaces).

## 55. The public dev keys

- **Decision:** at the start of `serve`, the server compares the SHA-256 fingerprints of `SCYLLA_TOKEN_PRIVATE_KEY`, `SCYLLA_SPICEDB_KEY`, `SCYLLA_SECRET_KEY` and each key of `SCYLLA_TOKEN_PUBLIC_KEYS` (trimmed, in lower case) with the fingerprints of the dev keys of the `.env` files and of the public key of the dev signing key. With a dev key, a server that is not local does not start, and the error names the setting and the reason. A local server binds a loopback address, does not trust the headers of a proxy (`SCYLLA_TRUST_FORWARDED_HEADERS`), and has its URL and the URL of the web app (`SCYLLA_API_URL`, `SCYLLA_APP_URL`) on `localhost` or a loopback address. A local server with a dev key logs a `WARN`. A unit test checks that each key of `.env` and the public dev key have their fingerprint in the list.
- **Why:** the `.env` files are in a public repository, so each person has these keys. A server with them accepts tokens that anyone can sign. The public key of the dev signing key in `SCYLLA_TOKEN_PUBLIC_KEYS`, for example after a rotation away from the dev key, also accepts these tokens. A server behind a proxy or with a public URL is reachable even when it binds a loopback address. The code keeps only the fingerprints, so a search for the keys does not find the code.
- **Not kept:** no dev keys in `.env` (each developer would have to make keys before `just run`); a check of the length of a key (a long dev key is still public).

## 56. A project changes

- **Decision:** `UpdateProject` changes the name and the description of a project. A field that the request does not set does not change. The name has 1 to 100 characters after trim, on one line. The description has at most 1024 characters after trim, can have line breaks and tabs but no other control character, and an empty description removes it: `projects.description` is `NOT NULL DEFAULT ''`. `CreateProject` also takes a description. The route permission is `update_project`: `edit` on the project (its admins and editors) and `work` on its workspace (its owners, admins and members). The last change wins: no version field. An unknown project gives `PERMISSION_DENIED`. Each display name (`Name`: a user, a workspace, a project) is one line: a line break or another control character gives `INVALID_ARGUMENT`.
- **Why:** the web app has a dialog that changes the name and the description, and its cards show the description. A member of a workspace creates projects, so it also changes them. The old product had a version check, but no client sent a version, so the check guarded only the time between the read and the write of the server. A line break in a name breaks a list or a title, and Postgres refuses a NUL character with an internal error.
- **Not kept:** `is_active` and `SetProjectActive` (stored, never enforced, and no client used them); a version field and `ABORTED`; a description that can be `NULL` (two values for "no description"); the one-line rule for the projects only (one rule for each display name).

## 57. The secrets of a project

- **Decision:** a secret belongs to one project: `secrets (id, project_id, name, sealed_value, created_by, created_at, updated_at)`, with `UNIQUE (project_id, name)`. `SecretService` (package `scylla.projects.v1`) has `CreateSecret`, `UpdateSecret` (a new value, the name does not change), `DeleteSecret` and `ListSecrets`. A name has 1 to 128 ASCII letters, digits, dots, dashes or underscores after trim, and keeps its case. A check of the table holds this form. A name in use in the project gives `SECRET_NAME_IN_USE`. A value has at most 65536 bytes, and the server keeps it as it is. No answer holds a value: the message `Secret` has the id, the project, the name, the author, `created_at` and `updated_at`. `SecretValue` shows `***` in `Debug` and has no `Display`. `ListSecrets` gives the secrets in the byte order of their names (`COLLATE "C"`), and the token of a page is the last name. The route permissions are on the project and on its workspace: `create_secret`, `update_secret` and `delete_secret` are `delete` on the project (its admins) and `manage` on the workspace (its admins), and `list_secrets` is `edit` on the project (its admins and editors) and `work` on the workspace (its admins and members). The owners of the workspace pass with no role. These permissions are in the definition `project` and in `ProjectHolder`, as the routes of `AccessService` on a project. `UpdateSecret` and `DeleteSecret` name the secret: the route reads its project and the workspace of the project from Postgres. An unknown secret and a refusal get the same answer, and this answer names the secret, not its project. A secret goes with its project (`ON DELETE CASCADE`). The delete of a secret that a pipeline names passes: the next run of the pipeline fails with `NOT_FOUND`. A secret has no hook kind.
- **Why:** a pipeline names a secret by its name in its project, so the name is unique there and does not change. Only the run of a pipeline needs a value. A value in an answer goes to a browser, a log or a proxy. The editors of a project and the members of the workspace write the pipelines, so they see the names of the secrets. The byte order does not change with the collation of the database, and a name is unique in its project, so the last name is a correct cursor. A secret has no use without its project. No edition needs a hook on a secret now: the kind `secret` and its hook calls come with the first edition that needs them.
- **Not kept:** secrets of a workspace (the web app and the pipelines use the secrets of a project); a description of a secret (it is not in the decisions of the migration); a new name in `UpdateSecret` (a pipeline would lose its secret); pages in id order (the web app shows the names in order); a check of the pipelines before a delete (the user allows the delete, and the web app warns); a project delete that a secret stops (the secrets are part of the project).

## 58. The encryption of the secrets

- **Decision:** `Sealer` encrypts with XChaCha20-Poly1305 and the key of `SCYLLA_SECRET_KEY`. A sealed value is its random nonce (24 bytes), then the ciphertext. `seal_with` and `open_with` take associated data: the value of a secret is sealed with the 16 bytes of the id of its secret (`Id::to_bytes`), so a sealed value copied to another row does not open. The client secrets of the identity providers use `seal` and `open`, with no associated data. With no key, the server starts, and `CreateSecret` and `UpdateSecret` give `FAILED_PRECONDITION` with the reason `SECRET_KEY_MISSING`, after the check of the route. `ListSecrets` and `DeleteSecret` need no key. The crate-internal `secrets::service::reveal` opens the value of a secret of a project by its name, for the dispatch of a job. No route calls it yet.
- **Why:** with the associated data, a person who can write to the database cannot move a value to a secret that this person can use, for example in another project. The bits of an id do not change with the text form of the ids (see 9). One key serves the two uses, and the associated data keeps them apart: a value of a project does not open as a client secret, and the reverse. An install with no secrets starts with no key. The check of the route comes first, so a caller with no right learns nothing about the key.
- **Not kept:** no associated data (in the old product, a ciphertext could move to another secret); the id of the project in the associated data too (the id of a secret is unique); a key id and a tool for the rotation of the key (a later change); a dev key in a file of settings (the key of `.env` is guarded, see 55).

## 59. The logs

- **Decision:** one subscriber writes the logs of `serve` and of the commands to stderr, in the format of `SCYLLA_LOG_FORMAT`: `pretty` for a person, `json` for a machine, or `auto` (the default), which is pretty when stderr is a terminal, else JSON. The pretty lines have colors only in a terminal, and not with `NO_COLOR`. With no `RUST_LOG`, the filter is `info`, and `warn` for `sqlx`, `hyper`, `h2`, `tonic`, `tower` and `tower_http`. `RUST_LOG` replaces this filter.
  - **One line for each call.** The layer `RequestLog` opens a span `rpc` for each call, with a new request id (an `Id`, UUIDv7 today), the route, and the IP address of the client by the rule of the sessions (see 45). `Gate::authenticate` records the actor and its kind on this span. At the end of the answer, the layer logs one `rpc` event with the code and the duration. The gRPC code comes from `grpc-status` in the headers of an answer with no message, or in the trailers at the end of the stream, never from the HTTP status. The `ErrorInfo` reason and metadata and the field violations come from `grpc-status-details-bin`. A browser route (`/auth/...`) logs its HTTP status. A call that stops before its end (a timeout, a client that goes away) logs `CANCELLED`. The level of the line is `ERROR` for a failure of the server (`INTERNAL`, `UNKNOWN`, `DATA_LOSS`, `UNAVAILABLE`), `WARN` for a refusal (`PERMISSION_DENIED`) and a call that stops, and `INFO` for the other codes.
  - **Placement.** The layer is inside the gRPC-Web layer, so it sees the gRPC answer and its trailers, and the browser routes have their own copy of the layer. The CORS layer is outside it: a preflight gets its answer from CORS and logs nothing. Each answer has its request id in the header `x-request-id`, and CORS shows this header to a web app.
  - **Pretty.** `HH:MM:SS.mmm` in local time, a tag (`OK`, `DENIED`, `REFUSED`, `INVALID`, `NOT_FOUND`, `UNAUTH`, `ERROR`...), `Service.Method` with no package, the duration, the actor (`anonymous`, or its kind and a short id: `user ..00000a1f`) and the IP address, in aligned columns. A refusal or an error adds a second line under the route: the permission and the object of a refusal of the gate, the reason and the metadata of a refusal of a rule, the fields of a bad request, the error of a failure, or else the message.
  - **JSON.** One object for each line: `ts` (RFC 3339 in UTC, with milliseconds), `level`, `event` (`rpc`, the name of a business event, or `log`), `rpc`, `code` (or `status` for a browser route), `ms`, `actor`, `actor_kind`, `ip`, `request_id`, then the details (`permission`, `object`, `reason`, `metadata`, `violations`, `message`, `error`) and the fields of the event. Each line of a call has its request id.
  - **One line for each fact.** The refusal of the gate (`access.refused`, see 53) and the error of a failed call (`request.failed`) go on the line of their call.
  - **Business events.** A fact that an operator must see is an `INFO` event after the commit, with a stable name in its field `event`: `role.created`, `role.updated`, `role.deleted`, `account.created`, `account.verified`, `account.signed_in` (with the method), `account.signin_failed` (with the masked identifier and the reason), `account.locked`, `app.signed_in`, `app.created`, `app.joined`, `app.key_added`, `app.key_revoked`, `app.deleted`, `agent.connected`, `agent.disconnected`, `job.created`, `job.dispatched`, `job.ended`, `job.failed` (`WARN`, a failed dispatch), `job.orphaned` (`WARN`), `job.cancelled`, `job.deleted`, `pipeline.deleted`, `trigger.created`, `trigger.fired`, `trigger.failed` (`WARN`), `trigger.deleted`, `password.reset_requested`, `password.changed`, `email.change_requested`, `email.changed`, `mail.sent` (the kind and the masked recipient), `mail.failed` (`WARN`), `session.revoked`, `user.enabled`, `user.disabled`, `user.deleted`, `admin.granted`, `admin.revoked`, `role.granted`, `role.revoked`, `invitation.created`, `invitation.accepted`, `invitation.resent`, `invitation.revoked`, `workspace.created`, `workspace.deleted`, `owner.added`, `owner.removed`, `secret.created`, `secret.updated`, `secret.deleted` (the name or the id, never the value). In the pretty format, an event has its own line with a tag (`AUTH`, `APP`, `JOB`, `MAIL`, `ADMIN`, `ACCESS`, `WORKSPACE`, `SECRET`). A task that a call starts (a mail after the answer) keeps the span of its call.
  - **No secret.** An email is masked (`s***@gmail.com`), and so is the identifier of a sign-in (`a***` for a handle). No line has a password, a token, a cookie, the value of a secret, the body of a mail or its link. The path of a browser route has no query, so the code and the state of a sign-in stay out.
- **Why:** the line of `tower_http` had the full URI, the HTTP version, the module, a line for each preflight, HTTP 200 for each gRPC answer, no actor and no business event. An operator now reads one line for each call with its real result, and the cause of a refusal under it. A machine gets the same facts as fields. The request id links the lines of a call, and a person can give it in a report of a problem. A log goes to many people and tools, so it has no secret and no full email. The `time` crate cannot read the local offset in a process with many threads on Unix, so the local time comes from `chrono`.
- **Not kept:** the `TraceLayer` of `tower_http` (no gRPC code, HTTP 200 for each call); the formatters of `tracing-subscriber` (their JSON nests the fields of the spans, and they cannot put a refusal on the line of its call); the layer outside gRPC-Web (it sees a gRPC-Web body, with the trailers in the body); a line at the start of each call (two lines for each call); a request id that the client sends (a client can write any text: a later change, behind a trusted proxy); the request id on the pretty line (too long for a person: the JSON line has it); a separate tag for a timeout (the layer cannot tell a timeout from a client that goes away).

## 60. The Apps

- **Decision:** an App is the machine identity of a workspace: an actor of kind `app` with a row in `apps (id, workspace_id, name, runner, created_by, created_at, last_seen_at, the host columns)`. `runner` is `true` for an agent, an App that runs jobs, and `false` for a client such as a CI or a script. `AppService` has `CreateApp`, `GetApp` (with the keys), `ListApps` (one workspace, a filter on `runner`, pages in id order), `DeleteApp`, `CreateJoinCode`, `AddAppKey` and `RevokeAppKey`. `CreateApp` gives a join code: 32 random bytes, valid 15 minutes, one use, and `app_join_codes` keeps only its SHA-256 hash. A new code stops the open codes of the App. The machine makes its Ed25519 key pair and calls `TokenService.JoinApp` with the code and its public key, and gets the App id and the key id. A key is in `app_keys (id, app_id, public_key, created_at, revoked_at)`. A revoked key keeps its row, so `GetApp` shows it. The token of an App is bound to its key (see 8): a revoked key or a deleted App stops it at once. A delete removes the row, its keys and its codes, removes the roles of the App (`Gate::delete_subject`), and closes its stream. The actor stays (see 44). The routes on one App have a definition `app` with `nil` permissions, so only the roles of its workspace give them: `get_app` is `read`, and `delete_app`, `create_join_code`, `add_app_key` and `revoke_app_key` are `manage`, as `create_app`. `list_apps` is `read` on the workspace. An unknown App and a refusal get the same answer, which names the App, not its workspace. `ListAccess` shows the name of an App as its display name. A new App has no role: an admin gives it one with `Grant`.
- **Why:** a CI, a script and an agent are all machines of a team, with the same key pair and the same roles; only an agent runs jobs. With a join code, the admin copies one short-lived text to the machine, and the private key never leaves the machine. A key bound to the token makes a revocation act at once, as the migration decided, with one indexed read in the check of the token. The definition `app` gives a refusal that does not tell the workspace of an App to a stranger.
- **Not kept:** the server makes the key pair and shows the private key one time (the server sees a private key); the admin pastes a public key (the old `RegisterAgent`: a copy from the machine to the browser and back); a secret of an App (see 8); `SetAppActive` (decision 73 adds `DisableApp` and `EnableApp`); a version of a token at the App level (a revocation of one key would stop the tokens of each key); an App outside a workspace.

## 61. The stream of an agent

- **Decision:** an agent opens `AgentService.OpenStream`, a bidirectional stream, with its token. The route permission is `open_stream` on the caller itself, and an App with `runner = false` or another actor gets `NOT_A_RUNNER`. The first message is a `Hello` with the host (version, OS, architecture, host name, CPUs, memory, capacity from 1 to 256 with 0 as 1, container runtime), within 30 seconds. The server stores the host and `last_seen_at` in the row of the App, answers `Welcome` with the expiry of the token, and records the stream in an in-memory registry. A `Renew` carries a new token from `ExchangeAppAssertion`: the server checks it as at the start (the gate, the same actor, the route permission) and answers `Renewed`. At the expiry of the last token, the server ends the stream with `UNAUTHENTICATED`. A second stream of the agent ends the first with `ABORTED`, and so do `RevokeAppKey` and `DeleteApp`. `last_seen_at` changes at the hello, at each renewal and at the end. `GetApp` and `ListApps` give `connected` from the registry. The server timeout of a request stops only the start of a stream, not its messages.
- **Why:** a stream gives the jobs to an agent at once and stops a job at once, and the bound of a token stays 10 minutes, as each other request has (see 6). A check of each new token on the stream keeps zero trust on a long call. One server instance needs no shared store of presence. `ABORTED` tells the agent to connect again: a revoked key then fails at the gate with `UNAUTHENTICATED`, which ends the agent.
- **Not kept:** a check at the start only (a stream could outlive a revoked key); unary poll calls (no instant dispatch or cancel); a heartbeat row in Postgres (a write each few seconds for each agent); `last_seen_at` at each message (a write for a field that the UI hides while the agent is connected); the jobs, the placement by capacity and container runtime, and the role `runner` (they come with the pipelines and jobs).

## 62. The pipelines

- **Decision:** a pipeline belongs to one project: `pipelines (id, project_id, workspace_id, created_by, name, nodes, version, created_at, updated_at)`, with the workspace of the project copied at the creation. The nodes are a `jsonb` column. A pipeline has 1 to 256 nodes with unique ids (1 to 128 lower case letters, digits, dashes or underscores). The needs of a node name other nodes one time each, and the graph has no cycle (the order of Kahn). A node runs a command (`exec`, a program and its arguments, with no shell) or a script (`sh` or `bash`, at most 1 MiB). It has at most 128 environment variables with unique names, a name does not start with `SCYLLA_`, and a value is a literal or the name of a secret of the project. The timeout is 1 to 604800 seconds (0 gives 3600), the retries 0 to 10, the work folder is relative with no `..` part, and the runtime is a process or a container of an image. The JSON of the nodes has at most 8 MiB. A bad value gives `INVALID_ARGUMENT` with its path, for example `nodes[2].env[0].name`. `PipelineService` has `CreatePipeline`, `GetPipeline`, `UpdatePipeline`, `DeletePipeline`, `ListProjectPipelines`, `ListWorkspacePipelines` and `RunPipeline`. `UpdatePipeline` carries the version that the client read: another version gives `ABORTED`, and a change adds one to the version. The new nodes replace all the nodes. `RunPipeline` gives `NOT_FOUND` for a secret that the project does not have. The routes are permissions of the project (`create_pipeline`, `update_pipeline`, `delete_pipeline` and `run_pipeline` are `edit`, `get_pipeline` and `list_project_pipelines` are `view`) and of the workspace (`work` and `read`); `list_workspace_pipelines` is `read` on the workspace. A pipeline goes with its project. The kind `pipeline` has `BeforeCreate` and `AfterDelete` hooks.
- **Why:** the web app has a JSON editor and a canvas of the same document, so the nodes are one document. A version in the request stops a lost change between two editors, which the old product did not stop. The path of a bad value lets the editor show the error at the value. The secrets are checked at the run, so a typo fails at once and not on the agent.
- **Not kept:** a table of nodes (no query needs one node, and the state machine changes one row); `ListPipelines` of the whole instance (no caller); a check of the secrets at the save (a secret can come after the pipeline); a version that only the server knows (the old product).

## 63. The jobs and their agents

- **Decision:** a job is one run of a pipeline: `jobs (id, pipeline_id, project_id, workspace_id, created_by, rerun_of, status, nodes, runs, need_container, agent_id, error, version, created_at, started_at, finished_at)`. `nodes` is the snapshot of the run, and `runs` the state of each node, in JSON. A job is `pending`, `running`, `completed`, `failed`, `cancelled` or `orphaned`. A node is `pending`, `running`, `completed`, `failed`, `skipped` or `cancelled`, with its attempt, its exit code and its error. The agent sends the events (`JOB_STARTED`, `NODE_STARTED`, `NODE_RETRYING` with the next attempt up to the retries plus one, `NODE_COMPLETED`, `NODE_FAILED`, `NODE_SKIPPED`, `JOB_COMPLETED` when each node completed or was skipped, `JOB_FAILED`), and `Job::apply` refuses an event that does not fit the state. An end of a job cancels each node that did not end. An error text keeps at most 4096 characters. The workspace has a relation `runner` and a permission `run_jobs`: an agent with this role gets, on its stream, the oldest pending job of its workspace with no agent (`FOR UPDATE SKIP LOCKED`), while it holds fewer jobs than its capacity. A job with a container goes only to an agent with a container runtime. The dispatch has the values of the secrets with `masked`, opened by `secrets::reveal`, and a secret that does not open fails the job with the reason. A message of an agent about a job that it does not hold, or that ended, gets a `Cancel`. `CancelJob`, `DeleteJob` and `DeletePipeline` tell the agent with a `Cancel` after the commit. After a new stream, the hello lists the jobs that the agent runs: a held job that it does not list ends as orphaned if it ran, or goes back to the pool if it waited, and a listed job that it does not hold gets a `Cancel`. A background task of each server releases each 30 seconds the jobs of the agents with no stream and no sign for 60 seconds. `RerunJob` makes a new pending job of the nodes of a job that ended, else `JOB_NOT_ENDED`. The lists of jobs give the newest first. The routes on a job are permissions of its project and of its workspace: `get_job`, `list_pipeline_jobs` and `tail_job_logs` are `view` and `read`, and `cancel_job`, `delete_job` and `rerun_job` are `edit` and `work`; `list_workspace_jobs` is `read` on the workspace, with an optional agent. The kind `job` has `BeforeCreate` and `AfterDelete` hooks.
- **Why:** the agent orders the nodes, so the server keeps only the state and checks each event. A snapshot keeps a job the same after a change of its pipeline. The role in the workspace, read again at each renewal, lets an admin give or take back the jobs from an agent with one `Grant`, and the agents of a workspace never get the jobs of another. A placement on the stream, in the order of the jobs, needs no scheduler: a run wakes the streams, and each stream looks again each 30 seconds. A cancel that is lost or that comes before the dispatch is safe, because each later message about the job gets a cancel.
- **Not kept:** unary calls to claim and report (the decision of the migration keeps the stream); one job for each agent (the capacity of the hello); labels of the agents (no user asked); a reaper per job with no grace (an agent that connects again keeps its jobs); a run hook (the base has `BeforeCreate`).

## 64. The logs of the jobs

- **Decision:** the agent sends the lines of a node in batches of 1 to 1000 lines, each cut at 64 KiB. One row of `job_logs (id, job_id, node_id, lines, created_at)` keeps one batch, with the lines in JSON. `TailJobLogs` is a server stream: it sends the batches after a cursor (the id of the last batch), of one node or of each node, then reads the table again each half second while the job runs, and ends after the last read of a job that ended. The background task deletes the batches older than `SCYLLA_LOG_RETENTION_DAYS` (30). The agent masks the values of the secrets in the lines.
- **Why:** a row for each batch has far fewer rows than a row for each line. A read by cursor works with many server instances and needs no memory, and a client that reconnects gives its cursor and gets each line one time. A retention keeps the table from growing with no end.
- **Not kept:** a row for each line; a broadcast in memory (one instance only, and a slow reader loses lines); `ListJobLogs` (no caller: the web app uses the tail); a store of files.

## 65. The triggers

- **Decision:** a trigger belongs to one pipeline: `triggers (id, pipeline_id, project_id, workspace_id, created_by, name, kind, schedule, sealed_secret, inputs, enabled, next_fire_at, last_fired_at, last_status, last_error, created_at, updated_at)`, with a name unique in the pipeline (`TRIGGER_NAME_IN_USE`). A trigger is `cron` (exactly 5 fields, UTC, checked with `croner`) or `webhook`. Its inputs are at most 128 variables with unique names (the rules of the variables of a node): a literal, or a JSON pointer (RFC 6901, empty or with a first `/`) into the body of a webhook only. Each node of a job gets the inputs, and a variable of the node with the same name wins. `TriggerService` has `CreateTrigger`, `GetTrigger`, `UpdateTrigger` (the name, the schedule, the inputs; not the kind), `DeleteTrigger`, `ListPipelineTriggers`, `SetTriggerEnabled` and `FireTriggerNow`. The routes are permissions of the project (`get_trigger` and `list_pipeline_triggers` are `view`, the others `edit`, as `run_pipeline`) and of the workspace (`read` and `work`). A fire starts a job with `trigger_id`, as the runner of the triggers of the workspace: an actor of kind `trigger_runner` in `trigger_runners (workspace_id, actor_id)`, made at the first fire. The fire records `ok` or `error` with the reason on the trigger. A webhook trigger gets a secret of 32 random bytes in hex, which the response gives one time, sealed with the id of the trigger as associated data; with no key, `SECRET_KEY_MISSING`. The route `POST /webhooks/{id}` has no token: it takes a body of at most 1 MiB, allows 60 requests to one trigger each minute (429), gives 404 for an unknown or stopped trigger, checks the HMAC-SHA256 of the body in `X-Scylla-Signature-256` or `X-Hub-Signature-256` (with or without `sha256=`, in constant time) before any write (401), answers a GitHub `ping` with 200, keeps the key of the delivery (`X-Scylla-Delivery`, `X-GitHub-Delivery`, or the signature) in `trigger_deliveries` so a second delivery gives 200 with no job, gives 422 for a body with no value at a pointer, and 202 with the id of the job. A failed fire forgets its key, so a retry of the sender fires. A loop in each server takes each 15 seconds the due cron triggers with `FOR UPDATE SKIP LOCKED`, writes their next time in the same transaction, then fires them; a missed time does not fire later. The loop also deletes the keys of the deliveries older than 7 days.
- **Why:** a trigger is only a way to start a run, so it has the rights of a run and gives no new right. A runner of the workspace keeps the author of a job when the person that made the trigger leaves, and it has no key and no role, so no request can act as it. A signature of the body works with GitHub and each sender of webhooks. The key of a delivery stops a second job when the sender sends again. The lock and the next time in one transaction fire each time one time with many servers.
- **Not kept:** an App row for the runner (an admin could delete it or give it a key); a version of a trigger (no editor writes a trigger at the same time as another); a token in the URL of a webhook (it goes to logs and proxies); a backfill of the missed times; the extension points for the HTTP routes and the background tasks of an edition (the webhook route and the loop are core code with the open streams of the agents and the key of the secrets; an edition point comes with the first edition that needs it, the GitHub App of the Enterprise edition).

## 66. The server serves the web app

- **Decision:** with `SCYLLA_WEB_DIR`, the server serves the files of the built web app on its own address, for each GET that no route takes: a path that is a file gives the file with its content type, and another path gives `index.html`, so a route of the web app loads. With no setting, the server serves the API only.
- **Why:** one domain for the API and the web app needs no CORS, and the session cookie stays first-party. The migration decided it for the cloud. The static files go through the same port and the same TLS as the API.
- **Not kept:** a separate static host as the only way (it stays possible with no setting); a cache policy in the server (the ingress or the hashes of the file names of the build give it).

## 67. The hooks of the memberships

- **Decision:** the core runs `BeforeCreate` of the kind `member` when a user joins a workspace: `Grant` of a role to a user on the workspace or on one of its objects (before the SpiceDB write, in its own transaction), `AcceptInvitation` (after the mark of the invitation, before the SpiceDB write, in the transaction of the accept), and `AddOwner` (role `owner`, in its transaction). The context names the member (`subject`), the object of the role as `kind:id` (none for an owner) and the role. A hook that refuses stops the call. `Revoke` runs `AfterDelete` of the kind `member` with the same facts, after the SpiceDB delete. `CreateInvitation` runs `BeforeCreate` of the kind `invitation`. The delete of a project names the project (`object`) in its `AfterDelete` context. An App gets no membership hook in `Grant`: only a user joins.
- **Why:** an edition limits the members of a workspace, so it needs each way a person joins, before the write. The facts of the role let an edition keep its own count of the roles in Postgres, so a lock of the workspace makes the limit strict. The hook of `Grant` commits before the SpiceDB write: a failed write leaves a seat that the next `Revoke` frees, never a role with no seat.
- **Not kept:** a membership hook that reads SpiceDB (a hook has only the Postgres transaction); a hook on each relationship write of the gate (a write of the gate is not always a person that joins).

## 68. The agent binary

- **Decision:** `scylla-agent` is a crate of this repository with a library and a binary, and it depends only on the protos. `join <url> <code>` makes an Ed25519 key pair, calls `JoinApp` with the public key, and writes a JSON file of mode 600 with the URL, the App, the key and the private key. `run` signs an assertion of 60 seconds with a random nonce for each token, opens `OpenStream` with a hello (the host, the capacity, the container runtime, the running jobs), and renews its token one minute before its expiry. After an end of the stream (`ABORTED`, an expiry, a network failure), it connects again after 1 second, then a wait that doubles up to 60 seconds, and from 1 second again after a stream of 30 seconds. A refusal of the token exchange or of the stream (`UNAUTHENTICATED`, `PERMISSION_DENIED`, `FAILED_PRECONDITION`, `NOT_FOUND`, `INVALID_ARGUMENT`) stops the agent. The messages of the jobs wait in one queue of 10000 while the agent connects again, so the jobs keep running. A job runs in `<workspace root>/<job id>`, deleted at its end unless `--keep-workspace`. The agent starts each node whose needs completed at once, runs at most the retries plus one attempts of a node (`NODE_STARTED`, then `NODE_RETRYING`), and at the first failure stops the running nodes and skips the others (`NODE_SKIPPED`), then sends `JOB_FAILED` with the reason; else `JOB_COMPLETED`. A step runs in its own process group, with an empty environment plus `PATH`, a `HOME` in the work folder, `LANG`, `LC_ALL`, `TERM=dumb`, `CI=true`, `SCYLLA_JOB_ID`, `SCYLLA_NODE_ID`, `SCYLLA_PIPELINE_ID`, `SCYLLA_PROJECT_ID` and the variables of the node. A script goes to a file of the work folder and runs with `sh -e` or `bash -o pipefail -e`. A container step runs `<runtime> run --rm` with the work folder in `/work` and the variables by name. A timeout, a cancel or a halt sends SIGTERM to the process group, then SIGKILL after 5 seconds (and `<runtime> kill` for a container). The lines of stdout and stderr lose the values of the secrets of 4 characters or more (`***`), are cut at 64 KiB, and go in batches of at most 500 lines or each 200 ms. At a stop (SIGTERM, Ctrl+C), the agent stops its jobs; the server ends them as orphaned after its grace.
- **Why:** the agent of the old product used a shared secret; this one keeps its private key, as decision 8 asks. A library lets the tests run a real agent against the real server. A process group stops the children of a script too. The queue keeps the events in order across a new stream, so a short network failure does not lose a job.
- **Not kept:** a sandbox or limits of resources for a process step (a later change; a container step isolates it); a report of the running jobs at a stop (the server finds them with its grace). Decision 70 adds Windows.

## 69. The import of the old product

- **Decision:** `scylla-ce import` reads the database of the old product (`SCYLLA_IMPORT_FROM`) with queries checked at run time, and writes into a base with migrations and no user (else `IMPORT_TARGET_NOT_EMPTY`). A user with a valid email comes over with `accounts::insert_user`: its email (in lower case, verified), its Argon2 PHC hash as it is, its display name (or its user name), its user name as a handle when the handle is valid and free, its personal workspace, and the state `disabled` for an old user that was not active. A user with no valid email stays out. A grant `system-admin` makes an instance admin. An organization becomes a workspace with a slug from its name: its `organization-admin` users are its owners, `organization-member` gives `member`, `organization-viewer` gives `viewer`, a custom role of kind `admin` gives `admin` and of kind `member` gives `member`; an organization with no imported user stays out. A project keeps its id (the bits of its ULID), its name and its description, with the first owner as its author; `project-admin` gives `admin`, `project-developer` and a custom role of kind `member` give `editor`, `project-viewer` gives `viewer`. A secret opens with the old key (`SCYLLA_OLD_SECRET_KEY`, no associated data) and is sealed again with the key of this base and its id; with no old key or no new key, it stays out. A pipeline keeps its id and gets its nodes in the form of this base (`deps` to `needs`, `command` and `args` to `exec`, a process runtime), checked by the rules of decision 62; a pipeline that breaks them stays out. The roles go to SpiceDB after the rows. The grants of the Apps, the Apps, the agents, the sessions, the jobs, the logs and the triggers stay out. The report names each row that stays out with its reason. A test loads the real schema of the old product (`fixtures/legacy_schema.sql`, from its migrations) and imports rows of each kind.
- **Why:** the old product has real users, and their passwords keep working because the hash format is the same. An id of a ULID keeps its bits, so a link to a project or a pipeline keeps working. A report lets the operator fix the rows that stayed out by hand.
- **Not kept:** an import into a base with users (a merge has no clear rule); a copy of the sessions (they die with the new tokens); an import of the Apps and of their secrets (decision 8: an agent joins again with its own key pair); an import of the jobs and of their logs (history with no use for a new run).

## 70. The agent on Windows

- **Decision:** the agent builds and runs on Windows too. On Unix, nothing changes. On Windows, a step runs in a job object (the crate `process-wrap`) and in a new console process group, so a Ctrl+C in the console of the agent does not go to the steps. A timeout, a cancel or a halt ends each process of the job object at once, with no grace. The end of a step is the end of each process of its job object. The environment of a step also keeps `SystemRoot`, `windir`, `ComSpec`, `PATHEXT`, `TEMP` and `TMP` of the agent, and `USERPROFILE` is the work folder, as `HOME`. A script runs with the `sh` or the `bash` of the `PATH`, for example the ones of Git for Windows. The file of the agent gets the access of its folder, with no mode 600. The default folder is `%LOCALAPPDATA%\scylla-agent`, with `agent.json` and `work`. The agent stops at Ctrl+C, Ctrl+Break, the close of its console, or a shutdown.
- **Why:** a developer on Windows can run a real agent next to a local server, with no container and no WSL. A job object keeps and ends a tree of processes, as a process group on Unix. The workspace forbids unsafe code, so a crate makes the calls to Windows; the crate `windows`, at the version of `process-wrap`, gives only the flag `CREATE_NEW_PROCESS_GROUP`. With no `SystemRoot`, many Windows programs do not start. `%LOCALAPPDATA%` is private to its user, as the mode 600 on Unix.
- **Not kept:** a stop with a grace on Windows (`CTRL_BREAK_EVENT` needs a shared console, and a service has none); PowerShell or `cmd` as the shell of a script (the proto has `sh` and `bash` only). Decision 77 adds the Windows service.

## 71. The repositories

- **Decision:** the code of Scylla is in five repositories of `scylla-ops`. `scylla-ce` (public) has the core, the Community edition and the agent. `scylla-protos` (public) has the public protos and a subset of `google/rpc` for the clients; `scylla-ce` has it as a git submodule at `proto`, with an HTTPS URL. `scylla-ee` (private) has the Enterprise edition; it takes the crates of `scylla-ce` with cargo git dependencies pinned to one commit (`rev`), and has `scylla-ee-protos` (private) as a git submodule at `proto-ee`, with an SSH URL. `scylla-web` (public) has `scylla-protos` as a git submodule at `protos`. The lint of the protos runs in their repositories. The history of each repository comes from one folder of the migration repository, with `git subtree split`.
- **Why:** one contract serves the backend, the Enterprise edition and the web UI, and each consumer pins the commit that its code uses. A public submodule with HTTPS lets CI and cargo get it with no key. A pinned `rev` makes each Enterprise build use one known version of the core.
- **Not kept:** one repository for all the code (the Enterprise code stays private); a package registry for the protos (a submodule is enough for two consumers).

## 72. The agents of some projects

- **Decision:** a project has a relation `runner` and a permission `run_jobs`, and `AccessService.Grant` gives the role `runner` on a project. At the hello and at each renewal, the stream of an agent reads its scope: each project of its workspace with the role `runner` of the workspace (decision 63), else the projects where it has the role `runner` (a reverse lookup in SpiceDB), else no job. The placement takes the oldest pending job of the workspace in this scope. The secrets of a job go only with its dispatch, so an agent of some projects gets the secrets of these projects only.
- **Why:** a team can keep one machine for one project, for example a deploy agent with the secrets of production, and let the other projects use other agents. The scope comes from the roles, as each other right, so one `Grant` or `Revoke` changes it at the next renewal.
- **Not kept:** a list of projects in the row of the App (a second store of rights); a scope of the secrets apart from the jobs (no route reads the value of a secret).

## 73. Disable and enable an App

- **Decision:** `DisableApp` sets `disabled_at` on the App; a second call keeps the first time. In the same transaction, each job that its agent holds goes: a running job ends as orphaned, and a job that did not start goes back to the pool. Then the stream closes. The token check refuses each token of a disabled App, and `ExchangeAppAssertion` refuses its key with `FAILED_PRECONDITION` and the reason `APP_DISABLED`, after the check of the signature. The agent sorts `APP_DISABLED` apart from the refusals for good: it stops its jobs, then connects again with its growing wait, so it comes back at its next try after `EnableApp`. The admins of the workspace call the two routes (`disable_app` and `enable_app` are `manage`).
- **Why:** a team stops a machine for a time (a maintenance, a leak under study) and keeps its keys, its roles and its history, which a delete loses. Only the holder of a key that signs learns the reason. An agent that waits needs no new login on its machine.
- **Not kept:** a pause that keeps the running jobs (a disabled machine stops at once); a stop of the process of the agent (an admin would need the machine to start it again).

## 74. The names of the keys and their last use

- **Decision:** a key of an App has an optional name (`label`, 1 to 100 characters, one line). `JoinApp` and `AddAppKey` take it; an empty text gives no name. The agent sends the name of its machine at the join, from the system on each platform. `RenameAppKey` changes the name, for the admins of the workspace (`rename_app_key` is `manage`); a key of another App gives `NOT_FOUND`. Each `ExchangeAppAssertion` that passes sets `last_used_at` on the key and `last_seen_at` on the App, in the transaction that uses the nonce.
- **Why:** an App with keys on many machines needs a name for each key, so that an admin revokes the right one. The last use shows a key that no machine uses now, and an App that stopped.
- **Not kept:** a name that the server makes from the host of the stream (a key exists before its first stream, and a non-agent App has no host); a separate log of each use (one time per key is sufficient for the screens).

## 75. The number of jobs of an agent

- **Decision:** each App message has `running_jobs`: the number of jobs that its agent holds now, that is the jobs that it took and that did not end (`pending` with the agent, or `running`). `GetApp`, `ListApps` and `EnableApp` count them in one query for each call (a `GROUP BY` on the partial index `jobs_agent_id_idx`). `CreateApp` and `DisableApp` give 0, because a new App has no job and a disable releases each job. `ListJobs` with `agent_id` gives the jobs.
- **Why:** the screen of the agents shows the load of each agent next to its capacity, and the count comes from the jobs table, so it is always true after a restart of the server.
- **Not kept:** a count in memory in the registry (it is wrong after a restart, and it knows only the streams of this server); a list of the jobs in the App message (the page of the jobs has its filters and its pages).

## 76. The job stats of the agents

- **Decision:** `AgentService.GetAgentStats` gives the stats of one agent, and `ListAgentStats` gives them for each agent of a workspace with a job in the window. The window is the last 30 days in UTC, today included. A job counts on the day of its creation, and only when it ended: completed, failed, cancelled or orphaned. The stats also give the median and the 95th percentile of the run time (start to end) of the jobs that started and ended. Each stats message has the 30 days, also the days with no job. Postgres computes the counts and the percentiles (`count(*) FILTER`, `percentile_cont`, `date_trunc` in UTC) in two queries, and the domain fills the empty days. The readers of the workspace read the stats (`get_agent_stats` and `list_agent_stats` are `read`). The index `jobs_workspace_id_idx` is now on `(workspace_id, created_at)`.
- **Why:** the screens of the agents show the jobs of 30 days, the success rate, a line of each day, and the run times. The server computes them in one call for the list, so the browser does not read the jobs of each agent. The counts only give numbers, so a reader of the workspace can read them like the list of the Apps.
- **Not kept:** a window that the caller sets (the screens use 30 days); the days in the time zone of the user (the server has no time zone of the user; UTC is the same for each reader); a median for each day (the line of each day shows the counts only); a table of counts that the server updates at each end (a second truth to keep correct).

## 77. The agent as a service, and its first start

- **Decision:** `scylla-agent run --service` is the Windows service `ScyllaAgent`: the service control manager starts it, a stop of the service or a shutdown stops the jobs as Ctrl+C does, and the logs go to `agent.<date>.log` next to the file of the agent, 7 days at most. The crate `windows-service` makes the calls to Windows. On Linux and macOS, systemd and launchd run `scylla-agent run` with no change. `run` also takes `--url` and `--join-code` (`SCYLLA_URL`, `SCYLLA_JOIN_CODE`): when the file of the agent does not exist, it joins first and writes the file; when the file exists, it reads it and does not use the code. This reverses the "Not kept" of decision 70 for the service.
- **Why:** a machine that runs jobs must start the agent at boot, before a user signs in, and restart it after a failure. Windows only does this for a program that talks to the service control manager. A container or a script that starts the agent has only a join code at its first start, and must keep the same key after a restart.
- **Not kept:** a scheduled task at boot (no clean stop, so each restart orphans the running jobs); a join at each start (each restart would add a key to the App); the Windows event log for the logs (a file is easier to read and to send).

## 78. The install of the agent in one command

- **Decision:** the server serves `GET /install.sh` (Linux and macOS) and `GET /install.ps1` (Windows), with its URL, its version and the folder of the downloads in single quotes of each language. A script downloads `scylla-agent-<target>.tar.gz` or `.zip` and `SHA256SUMS`, stops at a wrong checksum, installs the binary, joins with the code, and starts a service: systemd with the user `scylla-agent` (in the group `docker` when Docker is there), launchd with the user of the command (it sees the Docker of that user), or the Windows service `ScyllaAgent` with its folder `%ProgramData%\scylla-agent` for `SYSTEM` and the administrators only. `--no-service` installs and joins only. The folder of the downloads is the GitHub release of the version of the server, or `SCYLLA_AGENT_DOWNLOADS_URL`. The workflow `release` builds the agent at each tag `v*` (static musl binaries on Linux, macOS and Windows on x86_64 and aarch64), publishes the archives with `SHA256SUMS`, and pushes the image `ghcr.io/scylla-ops/scylla-agent` (Debian slim, with `git` and `bash`), which joins at its first start with `SCYLLA_URL` and `SCYLLA_JOIN_CODE`.
- **Why:** a team adds a machine with one command from the screen of the agent, with no manual step. A script from the server knows the URL and the version of that server, so the agent always matches its server. The checksum stops a broken or changed download. A static binary runs on each Linux distribution.
- **Not kept:** packages for each system (apt, rpm, Homebrew, winget: a store and a key for each); downloads from the server itself (a server with no access to the internet sets `SCYLLA_AGENT_DOWNLOADS_URL` to its own mirror); a Docker CLI in the image (a container step needs the runtime of the host, so a container agent runs the shell steps only).

## 79. The API tokens of the Apps

- **Decision:** an admin of the workspace creates an API token of an App (`CreateAppToken`) with a name and a life of 7, 30, 90 or 365 days (90 when not set). The secret is `scya_` and 32 random bytes in URL-safe base64; the response gives it one time, and the table `api_tokens` keeps only its SHA-256 hash, with a hint (`scya_...` and its last 4 characters). `TokenService.ExchangeApiToken` takes the secret and gives a short token of the App, bound to the API token (`api_token` fact in the first block, `Binding::ApiToken`), and records the last use of the token and the last sight of the App. The check of each request refuses a short token whose API token is revoked or expired. A disabled App gets `APP_DISABLED`; a deleted App loses its API tokens. The readers of the workspace list the tokens (`list_app_tokens` is `read`); the admins create and revoke them (`manage`). The table also takes the personal tokens later, by their actor.
- **Why:** a script, a CI job or a service calls Scylla with one secret, with no key pair and no signed assertion. A hash with no salt is sufficient for a random secret of 256 bits, and a lookup by its hash is fast. A short token per call keeps the check of each request the same as for the other tokens, and a revocation stops each short token at once.
- **Not kept:** a token that never expires; the secret in a second read (a lost secret needs a new token); argon2 for the hash (the secret is random, not a password); a direct use of the secret on each gRPC call (the HTTP/JSON gateway takes it later, with a cache); pages for the list (an App has few tokens).

## 80. The limits of the API tokens

- **Decision:** each API token has limits (`TokenLimits`): a preset and a list of projects. Read-only (the default) allows the methods whose names start with `Get`, `List`, `Check` or `Tail`; deploy adds `RunPipeline`, `FireTriggerNow`, `CancelJob` and `RerunJob`; full adds nothing; custom allows 1 to 200 methods of the token (`<package>.<Service>/<Method>`). A list of 1 to 100 projects allows only the checks on one of these projects: a route on a workspace or on the caller (`ListProjects`, `CreateProject`) is refused. `ExchangeApiToken` adds the limits to the short token as a second Biscuit block (`check if operation($op), ...`, `check if resource("project", $id), ...`), which the holder cannot remove. The roles of the actor still decide each check; the limits only remove rights.
- **Why:** a token for a CI job or a dashboard needs less than its App, and a leaked token must do as little as possible. Biscuit already checks the operation and the object of each request (decisions 7 and 26), so the limits need no new check in the server and no new column in the check of each request.
- **Not kept:** limits on the App itself (each token has its own); a list of projects for the routes on a workspace (they would need a filter in each handler); a regex in the checks (the string checks of Biscuit are sufficient, and the method names are fixed).

## 81. The App creators

- **Decision:** the role `app_creator` of a workspace (`AppHolder::APP_CREATOR`) gives `create_app`, with no other right in the workspace; the admins keep `create_app` (`manage + app_creator`). The members and the viewers do not get it. `CreateApp` writes the relation `creator` from the new App to its caller, and each route on an App also passes for its creator (`permission ... = creator` on `app`). So an App creator manages the Apps that it created (keys, join codes, API tokens, disable, delete), and nothing else. `DeleteApp` removes the relations of the App. The web app asks `CheckPermissions` for `create_app` on the workspace before it shows the button.
- **Why:** a team gives the creation of Apps to some people without the other rights of an admin, and a person who creates an App must be able to make its credentials. A relation on the App keeps this right with the App, and the delete removes it.
- **Not kept:** `create_app` for the members by default (an App can get roles and act with no person); a creator that also reads the list of the Apps of the workspace (that needs `read` on the workspace, from a role); a field `can_create_app` in a message (`CheckPermissions` already answers each permission).

## 82. The personal tokens and their switches

- **Decision:** a user creates personal tokens (`PersonalTokenService`): API tokens of its own actor, with the prefix `scyp_`, the same lives (7 to 365 days) and the same limits as the tokens of the Apps. `ExchangeApiToken` takes them and gives a short token of the user, inside the limits. A short token that came from an API token cannot create an API token (`check_maker`), even with the full preset. An instance admin turns the personal tokens off and on (`SettingsService`, table `instance_settings`, one row): when they are off, the check of each request refuses the short tokens of the personal tokens at once, and the creation and the exchange give `PERSONAL_TOKENS_DISABLED`. An admin of a workspace turns them off for the workspace (`UpdateWorkspace.personal_tokens_enabled`, column `workspaces.personal_tokens_enabled`): the gate refuses each check of a personal token whose workspace (named by the check, or the workspace itself) refuses them. `ListPersonalTokens` tells if the instance allows them and which workspaces of the caller refuse them. `GetInstanceSettings` counts the active personal tokens. The deletion of a user deletes its personal tokens.
- **Why:** a person runs a script or a tool as themselves without a password and without an App. An admin who fears a leak stops each personal token at once, for the instance or for one workspace, and the other credentials keep working. A token that makes tokens would let a leak outlive its revocation.
- **Not kept:** a check of the switch of the workspace for the routes on the caller (`ListProjects` lists the projects of each workspace of the user; its items are names only); a shorter longest life for the personal tokens (the user chose 1 year, as for the Apps); a count of the tokens that a workspace switch stops (a personal token belongs to no workspace).

## 83. The CI identities of the Apps

- **Decision:** an admin of the workspace, or the creator of the App, adds CI identities to an App (`AddCiIdentity`): a provider (GitHub Actions or GitLab CI), an issuer (the public service when not set), a repository, an optional Git ref, an optional environment, and limits (read-only when not set). `TokenService.ExchangeCiToken` takes the App and the ID token of a CI job, and checks the token with the keys of the issuer of each CI identity of the App (the OIDC discovery and JWKS, as for the identity providers; asymmetric signatures only; the audience is the URL of the server). The first CI identity whose rules fit gets a short token of the App, inside its limits: the same repository (`repository` on GitHub, `project_path` on GitLab), and the same `ref` and `environment` when it names them. A disabled App gets `APP_DISABLED`. The exchange records the last use of the CI identity and the last sight of the App.
- **Why:** a CI job calls Scylla with no secret to store and to rotate: the CI provider proves the job, and Scylla trusts only the repositories, refs and environments that an admin named.
- **Not kept:** a binding of the short token to the CI identity (a removed CI identity gives no new token; a given token ends in 10 minutes, and the App checks still apply at once); other providers (the user chose GitHub and GitLab first); the GitHub Action `scylla-ops/login` in this repository (it goes to its own repository, and calls `ExchangeCiToken`).

## 84. The HTTP/JSON gateway

- **Decision:** `POST /api/<package>.<Service>/<Method>` takes the proto3 JSON of the input of a unary method, and answers the proto3 JSON of its output. The gateway reads the messages with the descriptors of the protos (`scylla_proto::FILE_DESCRIPTOR_SET`, and the sets that an edition adds with `EditionBuilder::descriptors`; `prost-reflect`), and calls the method on the same layered gRPC routes in the process, so the gate, the route rule, the logs and the limits of the tokens are the same. An error answers the HTTP status of its gRPC code, with `code` (for example `PERMISSION_DENIED`), `message`, and the `reason` and the `fieldViolations` of its details. A bearer API token (`scya_`, `scyp_`) works directly: the gateway exchanges it with `ExchangeApiToken`, and keeps the short token until one minute before its end (10,000 at most); the check of each request still stops a revoked or expired API token at once, because the short token is bound to it. A streaming method gives `400`.
- **Why:** a script, a CI step or another tool calls Scylla with `curl` and JSON, with no gRPC client and no code generation, and with the same rights and the same checks as the gRPC API. One generic route follows each new method with no work.
- **Not kept:** routes for each method with `google.api.http` options (a second name for each method to keep); the streaming methods in JSON (the agents and the log tails use gRPC or gRPC-Web); the SDKs in this repository (they go to their own repositories, from the same protos).

## 85. The agent writes a failed attempt in the logs

- **Decision:** after each failed attempt of a node, the agent sends one line on stderr in the logs of the node: `scylla-agent: attempt <n> failed: <reason>`. The reason is the one of the `error` of the run: an exit code, a process that did not start, or a timeout. The agent also writes the reason in its own log, as a warning. A program that the agent does not find is named in the reason, and for a script on Windows the reason says how to install a shell: the error of the system does not name the program.
- **Why:** a process that does not start writes nothing, so its logs were empty, and a reader of the logs had no reason. The `error` of a run keeps only the last attempt; the line stays for each attempt. Each client that shows the logs gets the reason with no work.
- **Not kept:** a new stream for the lines of the agent (the prefix is enough, and the proto stays the same); the same line from the server (only the agent knows each attempt).

## 86. Custom roles and the roles of the instance

- **Decision:** a custom role is data in Postgres, in CE: `roles`, `role_permissions` and `role_grants`. A built-in role of a workspace or of a project stays a relation of the SpiceDB schema (see 19 and 30). The built-in role Instance admin stays the rows of `instance_admins` (see 42). A role has one level (`platform`, `workspace` or `project`), one kind of holders (`people` or `apps`) and one owner (the instance, or one workspace). The level, the holders and the owner do not change. A role of the platform level is for people only.
  - **The catalog.** A role holds permissions of the catalog (`scylla_domain::tenancy::catalog`): 38 for the platform level, 30 for the workspace level, 18 for the project level, and the area `job_execution` for the roles of apps. Each permission of the catalog gives a list of route permissions, as typed constants. A test finds each route of the schema that is not in the catalog. `RoleService` adds the permissions that the given ones depend on, and the implicit permissions of the level. What a built-in role of the schema holds comes from the schema (`Schema::gives`), so there is no second list.
  - **The gate.** After the actor itself, an instance admin and an owner, the gate reads the permissions that the roles that are rows give on the object, on its workspace and on the instance, in one SQL query. It asks SpiceDB only for the other permissions. A change of a role is live at once. A lookup adds the objects of the roles that are rows, so `gate.granted` shows them.
  - **An instance admin passes each route** on each object, with one read of `instance_admins`. A role of the platform level reaches each workspace and each project with its permissions. `workspaces.view` shows each workspace in `ListWorkspaces`, and `project.view` shows each project in `ListProjects`.
  - **No escalation.** A caller gives only what it holds: `CreateRole`, `UpdateRole` and `Grant` on the platform refuse a permission that the caller does not hold with `ESCALATION`. Only an instance admin gives or takes back the role Instance admin.
  - **The limit of the workspaces.** Each user can create a workspace, up to `workspace_limit` of `instance_settings` (1 by default), which the holders of the instance settings change. Over the limit, `CreateWorkspace` gives `WORKSPACE_LIMIT`. An instance admin has no limit. The personal workspace and an imported workspace do not count: only `counts_for`, which `CreateWorkspace` writes, counts. A delete frees the place. The creation locks the row of the user first, so two creations at the same time count one after the other. No role gives more workspaces.
  - **`Grant` and `Revoke` on the platform** give the roles of the platform level, to a user only (`ACTOR_NOT_A_USER`). In this change, a role that is a row has grants only on the platform: the other scopes come with the screens of the members. The table and the gate already read these scopes.
- **Why:** the design of the permissions (Figma, page "Permissions · roles and access") asks for roles that people make at runtime. The user chose a limit of 1 workspace for each user, not the role Workspace creator of the design, so the catalog has no `workspaces.create`. A row keeps one store for one fact: a role, its permissions and its grants are in one Postgres transaction, so decision 20 stays true, and the holders of a role and the time of a grant are one SQL query. A custom role does not change the schema of SpiceDB. Decision 42 stays: the right of an instance admin is in Postgres, also with SpiceDB down.
- **Not kept:** the role and its bindings as SpiceDB relationships, with one more term in each route permission (the name of a role is in Postgres and its permissions are in SpiceDB, so a change writes to two stores); Full control in a custom role (only the built-in admin roles have it, and a later route must not go to a custom role with no decision); a role of the old product as a Cedar policy; an edition of the built-in roles; deny rules; a role of the platform level for an App (an App belongs to one workspace).
- **Changes:** decision 19 (the roles are not all in SpiceDB), decision 28 (a role that is a row gives route permissions from the catalog), decision 42 (an instance admin passes on each object, not only on the platform), decision 43 (`ListUsers` tells the instance roles, the workspaces and the last sign-in, and the workspaces of a user come from one lookup for each user of the page). This replaces the "dropped by design" line of the migration notes.

## 87. The members of a workspace and of a project

- **Decision:** `Grant` and `Revoke` give and take back a custom role on a workspace and on a project, with its row in `role_grants`. `ListAccess` shows the owners, then the roles of the schema, then the roles that are rows.
  - **`ListMembers`** shows, with no pages, each member of a workspace or of a project, in name order, with each role and its scope. A member of a workspace has the roles on its projects. The instance admins are also in the list. A caller with only a role on a project does not see the roles on the workspace.
  - **`GetMemberAccess`** tells, for each permission of the catalog on a workspace or on a project, the roles that give it. A role on another project gives nothing here. It needs `get_member_access`, so a reader of a workspace and a viewer of a project can ask.
  - **`ListHeldPermissions`** tells the caller the permissions of the catalog that it holds on an object. The web app shows a locked role or a locked cell from this list. The server checks again at each change.
  - **No escalation everywhere.** `Grant` on a workspace and on a project and `CreateInvitation` refuse a role with a permission that the caller does not hold with `ESCALATION`, as on the platform. `Revoke` does not check this on a workspace or on a project, so an admin can take back each role. The check skips the permissions of a machine: no person holds them, and a Workspace admin must be able to give the role of an agent.
  - **An owner is not a Workspace admin.** The user chose to keep both. An owner is a row of `workspace_owners` (see 38), and the Workspace admin is a relation of the schema. A workspace can have no Workspace admin, and it always has an owner with all the rights. The rule of the last owner stays `LAST_OWNER`. The screens show an owner with its own chip.
  - **An invitation carries one built-in role of the workspace.** The user chose this. `CreateInvitation` does not take project roles or a custom role, and the screen says to give the project roles after the person accepts. A name finds a person only with `users.view`.
  - **The holders of a role.** `ListRoleHolders` gives at most 100 grants and the total. A list of the roles for a workspace counts the holders on the workspace and on its projects.
  - **The move of the holders.** `DeleteRole` with `move_to` gives the holders the other role, then deletes the role. The other role has the same level and the same holders, and the owner of the deleted role can use it. The caller must hold each of its permissions. The role Instance admin is not a target.
  - **The time of a grant.** `relation_grants` holds the time and the author of a grant of a role of the schema, because SpiceDB does not keep them. `Grant`, `AcceptInvitation` and the move write it. A grant from before this table has no time.
  - **`ListRoles` and `GetRole` on a workspace** need `read`, not `manage`, because a person that gives roles must see them. `workspace.view` gives them. To change a role still needs `workspace_roles.manage`.
- **Why:** the screens A3, A4, A5, E1 and S4 of the design of the permissions need these facts in one call. To read the roles on each project from the browser takes one call for each project. - **Not kept:** a time in SpiceDB (a relationship has no such field, and a caveat is not for this); pages in `ListMembers` (the list comes from one read of each scope, and the page filters it in the browser); a check of the escalation in `Revoke` on a workspace (the Workspace admin holds 29 of 30 permissions, and must be able to take back a role with `workspace.delete`).
- **Changes:** decision 86 (a role that is a row has grants on each scope). Teams, Check access and a resource level are not in this change.

## 88. A person needs a role in the workspace to get a role on a project

- **Decision:** `Grant` of a role on a project to a user with no role in the workspace of the project gives `FAILED_PRECONDITION` with `NO_WORKSPACE_ROLE`. A role in the workspace is an owner, a role of the schema or a role that is a row. When a user loses the last one, by `Revoke` or by `RemoveOwner`, the user also loses each role on the projects of the workspace, with the `AfterDelete` hooks of each one (see 67). An App is exempt, because decision 72 gives an agent only some projects. A grant from before this rule stays until someone takes it back: no migration deletes it.
- **Why:** the user chose the rule of section 6 of the design of the permissions. A role on a project gives more power to a person in a workspace, and it is not a way into a workspace. So the members of a workspace are the full list of the people with access to its projects, and one removal from the workspace ends all of the access of a person in it.
- **Not kept:** a project role for a person outside the workspace (the old share of one project); a migration that deletes the grants from before this rule (it takes access from a person with no one asking); the same rule for an App (it breaks decision 72).
- **Changes:** decision 31: a user gets a new share of one project only with a role in its workspace. The list still shows a project from an older share, and a project that an App has a role on. Decision 67: the end of the last role in a workspace runs the `AfterDelete` hooks of the roles on its projects.

## 89. The codes of a failed sign-in in a browser

- **Decision:** a browser route of a sign-in answers a failure with a redirect to the page `sign-in-error` of the web app: `?code=<code>&provider=<slug>`, and `&link=true` for a link. The codes are `access_denied`, `state_expired`, `email_unverified`, `signup_disabled`, `email_in_use`, `identity_in_use`, `account_inactive`, `session_required`, `redirect_uri_mismatch`, `provider_refused`, `provider_off`, `provider_unavailable`, `invalid_token` and `sign_in_failed`. The page is on the origin of `web_origins` that has the return address, or on `app_url`. The callback takes the state first, for the browser of the start, so a state works one time also when the provider sends an error. `ExchangeIdToken` for an account that is not active gives `FAILED_PRECONDITION` with `ACCOUNT_INACTIVE`.
- **Why:** a text answer of the API is a dead end for a person, and a card tells what to do. The URL has only a code and a slug, so no data of a person goes in a server log or a `Referer` header. The web app shows no text of this URL, because anyone can make it: the code is a key of its list, and the name of the provider comes from `ListSignInMethods`.
- **Not kept:** the error text of the provider in the URL (it comes from the query of the callback, and anyone can write it); the email of the person on the card of Figma (it would go in the URL); `UNAUTHENTICATED` for an account that is not active (the browser route needs a code, and a text match is not stable).
- **Changes:** decision 35: a refusal is no longer an HTTP status with a text.
